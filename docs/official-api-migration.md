# 공식 API 전환 계획

[수집 채널 적법성 근거](data-collection-compliance.md)에서 "공식 API로 옮겨야 한다"고 판정한 경로들을
**실제로 얼마나, 어떤 비용으로 옮길 수 있는지** 코드와 공식 문서를 대조해 조사한 결과다.

- **조사일: 2026-08-29**
- 조사 방법: 수집기별로 현재 코드가 쓰는 필드를 공식 API 응답 스펙과 1:1 대조하고, 그 결론을 다시 반증 검증했다
- ✅ 표시는 이 문서 작성자가 **공식 문서 원문 또는 저장소 코드에서 직접 확인**한 항목이다.
  확인하지 못한 것은 "확인 필요"라고 적었고, 확인한 척하지 않았다

## 2. 소스별로 짚어야 할 것

### 2-1. X — 삭제 작업에 가깝다

공식 API 경로는 **이미 구현돼 있고 배포판은 이미 그 경로로만 돈다.** 새 코드를 쓰는 일이 아니라
**웹 경로를 지우는 일**이다. 난이도가 '중'인 이유는 코드가 어려워서가 아니라 건드릴 파일이
core 1 + pipeline 2 + web 4 + 문서 2로 흩어져 있고 타입체크가 연쇄로 걸리기 때문이다.

**함께 처리하지 않으면 조용히 손해 보는 것 두 가지.**

1. **긴 글 본문이 오히려 짧아진다.** 현재 API 수집기는 요청 필드에 작성시각과 언어만 넣는다.
   이 API는 일정 길이를 넘는 글의 본문 필드를 잘라서 주고, 전체 본문은 **별도 필드를 명시적으로
   요청해야만** 온다. 지금 코드 그대로 전환하면 **긴 글에서 웹 경로보다 본문이 짧아진다.**
   이 본문이 그대로 LLM 분류·요약 입력이므로 표시 문제가 아니다.
   → 요청 필드에 전체 본문 필드를 추가하고 `전체본문 ?? 기본본문`으로 저장한다.
   접근 등급에 따라 400이 날 수 있으므로 기존 폴백과 같은 방식으로 빼고 재시도하는 경로가 필요하다.
2. **검색 질의 의미가 다르다.** API 경로는 키워드를 따옴표로 감싼 **정확 구문 검색**을 하고,
   웹 경로는 원문 그대로 던져 토큰 AND로 동작한다. **공백이 들어간 키워드**(별칭, 두 단어 조합)에서
   API 쪽이 구조적으로 더 적게 잡는다. 7일 창·리트윗 제외에 이어 **세 번째 수집량 감소 요인**이다.

**설계 결정 1건.** X 상한 필드의 기본 켜짐 값은 "기본 경로가 무료"라는 전제 위에 있다.
유료 API만 남으면 그 전제가 깨져, **저장된 설정이 없는 새 환경에서 X가 켜진 채 시작해 곧장 과금된다.**
기본값을 꺼짐으로 내려야 한다.

**비용 감각.** 회당 = 키워드 수 × 건수 상한 × 단가. 키워드 9개 × 20건이면 회당 약 $0.90,
6시간 주기(하루 4회)면 **월 약 $108**로 기본 예산 $50를 보름에 소진한다.
개발자 포털의 청구 주기당 지출 한도도 별도로 확인해야 한다(코드의 월 예산은 그 앞단 브레이크다).

> **정정.** 초기 조사는 "리트윗은 본문이 같아 도배 제거에 걸려 어차피 버려졌다"고 했는데 근거가 틀렸다.
> 도배 제거는 같은 본문이 3건 이상 모여야 동작하고 짧은 본문은 판정 대상에서 빠진다.
> 실제 이유는 리트윗 카드의 링크가 원글 ID를 가리켜 중복 판정에서 원글로 합쳐졌기 때문이다.
> 결론(실질 손실이 작다)은 유지될 가능성이 높지만 이 근거는 쓰면 안 된다.

### 2-2. Threads — 심사가 병목, 코드는 그 다음

**선행조건이 무겁다.** 기본 접근 등급에서는 앱에 역할이 부여된 사용자의 글만 검색된다.
타인의 공개 글을 검색하려면 상위 접근 등급이 필요하고, 그것은 앱 심사와 **비즈니스 인증**을
함께 통과해야 얻는다. 즉 **법인 실체 증빙 → 비즈니스 포트폴리오 등록 → 앱 심사** 3단계이고,
개발자 혼자 끝낼 수 없다. Meta가 기간을 보장하지도 않는다.

**필드 이득은 생각보다 작다.** 저장된 기존 데이터의 본문 길이는 평균 57자이고 상한에 닿은 행은 0.5%다.
다만 다른 방향의 이득이 있다 — 현재 본문은 DOM 컨테이너 텍스트라 말미에 참여 수와 UI 문자열이 섞이고,
상당수가 계정명으로 시작한다. 공식 API는 본문만 준다. **품질 개선이지 1:1 대응이 아니다.**

**중복 판정은 어느 쪽을 골라도 끊긴다.** 기존 저장분의 약 20%가 미디어 경로 꼬리가 붙은 형태라
API 응답과 일치하지 않는다(꼬리를 떼는 정규식이 들어오기 전에 저장된 행). 호스트도 다르다.
→ **1회 정규화 마이그레이션**을 넣거나 재적재를 감수한다. 최신순으로 가면 재적재는 수십 건 수준이다.

**문서화된 영구 커버리지 구멍.** 공식 문서는 민감하거나 불쾌하다고 판단한 키워드가 포함된 요청에
빈 배열을 반환한다고 명시한다. **승인 후에도 남는 제약**이고, 불만·사건 모니터링이 용도인 이 도구에서는
무시할 수 없다.

**수집량 서술을 정확히 하면**: 현재는 인기 성격 정렬이라 오래된 인기 글까지 끌어온다(30일 수집 265건 대
30일 작성 47건). 최신순으로 가면 이 꼬리가 사라진다. "승인 후 손실 없음"이 아니라
**"저장 건수는 47 수준으로 수렴하고, 대신 그것이 모니터링에 필요한 전부"** 라고 적어야 정확하다.

**구현 함정 3건.**
- 새 시그니처를 `(keywords, limit, service?)`로 잡으면 현행 호출부와 인자 순서가 어긋나
  서비스 자리에 숫자가, 상한 자리에 문자열이 **조용히** 들어간다
- 도배 제거 함수는 배열이 아니라 `{ kept, dropped }` 객체를 반환한다
- 회전 토큰(60일, 24시간 경과 후 갱신 가능) 선례가 이 저장소에 없다. 읽기 전용 환경변수에 다시 쓸 수 없어
  설정 표에 토큰과 발급시각을 저장하는 설계가 새로 필요하다. 파이프라인이 60일 넘게 멈추면
  토큰이 만료되고 갱신도 불가해져 사람이 다시 OAuth를 밟아야 한다 → **만료 임박 경고**가 필요하다

### 2-3. 구글플레이 — 7일 창이 가장 큰 손실

✅ **공식 문서 원문 확인**: *"You can retrieve only the reviews that users have created or modified within the last week."*
([Reply to Reviews API](https://developers.google.com/android-publisher/reply-to-reviews))

현재 스크래퍼는 최신순 정렬에 건수 상한만 있어 7일보다 오래된 리뷰도 받아 온다. 전환하면
**(a) 과거 백필이 불가능해지고 (b) 스케줄러가 일주일 넘게 멈춘 구간은 영구 유실**이다.
수집 주기 하한과 장애 알림 기준을 정책으로 정해야 한다.

> 🟢 **완화책이 있다.** 같은 문서가 과거 리뷰는 **Play Console에서 CSV로 내려받을 수 있다**고 안내한다.
> 최초 1회 과거분은 CSV로 채우고, 이후를 API로 잇는 방식이 가능하다.

✅ **페이지네이션 (원문 확인)**: 기본 10건, `maxResults`로 **최대 100건**.
현재 상한 설정(기본 200 / 최대 1000)은 단일 호출로 못 채운다. **다음 페이지 토큰을 따라가는 루프가 없으면
상한을 200으로 두고도 100건에서 조용히 끊긴다.** 초기 조사의 작업 목록에서 빠져 있던 항목이다.

✅ **쿼터 (원문 확인)**: GET **앱당 200회/시간**, POST 2,000회/일. 증액은 별도 신청.
앱 4종 규모에서는 여유가 있으나 상한을 올릴 때 계산에 넣어야 한다.

> **정정 — 자격증명은 3벌이 아니라 1벌이다.** 앞서 "Play Console 3벌"이라고 한 것은 틀렸다.
> **서비스 계정 하나를 만들어 그 이메일을 개발자 계정 3곳에 각각 초대**하면 된다.
> 필요한 것은 **키 3벌이 아니라 권한 부여 3건**이다. 따라서 설정에 "어느 계정 자격증명으로 읽는지"
> 필드를 넣는 작업과 환경변수 계정별 접미사 규칙은 **둘 다 불필요하다.**
> 다만 각 계정 관리자의 승인 3건이 필요하다는 점(일정을 개발이 통제 못 함)은 그대로다.
> 그리고 리뷰 읽기가 **'리뷰 답글' 권한**에 묶여 있어, "앱 접근 권한"이라는 뭉뚱그린 요청으로는 실행되지 않는다.
>
> 또한 초기 조사가 병목으로 든 "GCP 프로젝트 연결(소유자 권한 필요)"은 현재 공식 문서상
> **더 이상 필요 없다.** 선행조건이 생각보다 가볍다.

**국가는 라벨 손실이 아니라 성격 변화다.** 현재 국가 값은 메타데이터가 아니라 **어떤 리뷰 풀을 긁을지
정하는 조회 파라미터**다. 전환하면 작업이 9개(앱별 국가 수 합)에서 4개(앱 수)로 줄고,
상한 정의·총량 추산·대시보드 카드·국가 칩 필터까지 연쇄로 바뀐다. **화면 파급이 가장 넓은 항목**이다.

### 2-4. 앱스토어 — 가장 깨끗한 교체

필드 손실이 없고, 새 의존성이 없고(`node:crypto`로 ES256 서명 가능), 코드 변경이
파일 2개(수집기 교체 + JWT 유틸 신설)로 끝난다.

- ⚠️ **정렬 파라미터를 명시하지 않으면 최신 리뷰가 안 들어올 수 있다.** 조사에서 나온 지적인데,
  Apple 문서가 JS로 렌더돼 **원문 확인을 못 했다.** 구현 전에 실제 응답으로 확인할 것
- **기존 데이터 전량 재적재가 확정적이다.** RSS의 식별자 체계와 공식 API의 리뷰 ID가 달라
  중복 판정이 이어지지 않는다. 교체 전에 처리 방침(재적재 감수 / 마이그레이션 / 새 계열 시작)을 정해야 한다
- **.p8 개인키는 발급 시 1회만 내려받을 수 있다.** 분실하면 재발급이다
- 판매자 계정 2곳이므로 **키 2벌**이고, 수집기는 서비스별로 다른 키를 골라 쓸 수 있어야 한다

### 2-5. 다음 카페 — 🔴 API 전환이 리스크를 없애는 게 아니라 새로 만든다

**이것이 이번 조사에서 가장 뒤집힌 결론이다.**

적법성 문서는 카카오 다음 검색 API를 "합법 대체 경로"로 적었다. 그런데 카카오 운영정책을 확인하니
**저장 방식에 제약이 걸린다.**

✅ **[카카오 운영정책](https://developers.kakao.com/terms/ko/site-policies) 제5조(금지된 행동) 제20호 — 원문:**

> 앱에서 사용자 환경을 개선하기 위한 목적 외 다른 목적으로 카카오에서 받은 데이터를 캐시하거나
> 캐시 후 최신 데이터로 유지하지 않는 행위

이 도구는 수집물을 `items` 표에 **영구 적재하고 갱신하지 않는다**
(`ON CONFLICT ... DO NOTHING`, [store.ts](../packages/core/src/store.ts)). 조항의 후단에 정면으로 걸린다.

**즉 지금의 모바일 웹 파싱 경로가 오히려 근거가 낫다.** 그쪽은 다음 robots.txt가
`bbs_list`·`bbs_read`를 **명시적으로 Allow** 하고 있고, 저장 방식에 대한 계약상 제약이 없다.

- 🔴 **법무 판단이 선행이다.** 조항에 걸린다는 판단이면 이 교체는 진행하지 않는 것이 맞다
- 부수적으로 **"천장 제거"도 사실이 아니다.** 공식 응답의 `pageable_count`가 전체 건수보다 훨씬 작아
  키워드당 약 1,000건 근처에서 막힌다. 게시판당 20건 천장이 다른 천장으로 바뀌는 것이다
- 현재 수집량이 0이라 **서두를 이유가 없다**

> ⚠️ **같은 질문이 네이버에도 적용된다.** 지금 쓰고 있는 네이버 검색 API에 유사한 저장·캐싱 조항이
> 있는지 **확인하지 못했다.** 2026년부터 발급처가 개발자센터에서 NAVER Cloud로 바뀌어 적용 약관도
> 달라졌을 수 있다. **적법성 문서에서 네이버를 🟢로 표시했지만, 약관 층위는 미확인이다.**
> 카카오와 같은 조항이 있다면 현재 운영 중인 경로가 영향을 받는다. 법무 검토 항목에 넣어야 한다.

## 3. 교체해도 남는 공통 부담

- **식별자 연속성.** 앱스토어는 재적재 확정, Threads는 약 20%가 불일치 확정, 구글플레이는 미확인,
  다음 카페만 안전하다. 소스마다 "재적재 감수 / 1회 마이그레이션 / 새 계열 시작" 중 하나를
  **교체 전에** 정해야 한다. 조용히 넘어가면 화면 건수가 부풀고 분류 비용이 그만큼 다시 나간다
- **회전 자격증명 선례가 없다.** 이 저장소의 키는 전부 정적 환경변수다.
  Threads(60일 회전)와 구글플레이(1시간 토큰)는 새 설계가 필요하다
- **자격증명이 계정별로 갈려 있다.** 앱스토어 **키 2벌**, 구글플레이 **키 1벌 + 승인 3건**.
  발급·승인 일정을 개발이 통제할 수 없다
- **"자사 소유만" 제약.** 앱 리뷰 두 소스 모두 타사 앱 조회 능력이 사라진다.
  지금 수집 대상이 전부 자사 앱이라 손실은 0이지만, 경쟁 앱 모니터링 요구가 나중에 생기면
  적법한 경로가 없다. **요구사항 쪽을 미리 못박아 두는 편이 낫다**
- **최근 N일 창.** X와 구글플레이 모두 7일이다. 스케줄러가 그 이상 멈추면 그 구간은 영구 유실이므로,
  수집 주기 하한과 장애 알림 기준을 정책으로 정해야 한다

## 4. 교체 불가로 남는 구간 — 코드로 할 수 있는 완화 조치

커뮤니티 A는 공식 API가 없어 **대체 경로 자체가 존재하지 않는다.**
브라우저 기동 코드와 관련 분기도 그대로 유지해야 한다(Threads를 API로 옮겨도 마찬가지다).

> **커뮤니티 B는 2026-08-29 결정으로 껐다.** 아래 완화 조치 중 게시판형에 해당하는 항목은
> 되살릴 때를 대비한 기록으로만 남긴다. **지금 실제로 적용해야 할 대상은 커뮤니티 A 하나다.**
> 그리고 그것이 **유일하게 켜져 있는 커뮤니티**라 완화 조치의 가치가 오히려 커졌다.

### 이미 적용돼 있는 것

- 로그인 세션 미사용(둘 다 비로그인). **캡차 우회·지문 위조·IP 로테이션 없음**
- 요청·저장 상한: 상세 조회 30건 상한, 최대 페이지 수, 본문 800자 절단, 화면에서 상한 하향 가능
- **거부 신호 존중**: 게시판형은 403이 나는 통합검색을 우회하지 않고 목록 훑기로 대체했다.
  HTTP 오류는 경고 후 중단이며 예외를 던지지 않는다
- 도배 제거로 크로스포스팅 원문을 대표 1건만 저장
- 개인정보: 게시판형은 **작성자 닉네임을 아예 저장하지 않는다.**
  갤러리형의 작성자 값은 갤러리명이라 개인 식별자가 아니다
- 갤러리형은 배포판에서 강제로 꺼진다

### 없는 것 — 우선순위 순

| # | 항목 | 왜 |
|---|---|---|
| **1** | **차단 목록 필터** | 대상 사이트 robots.txt가 명시적으로 차단한 게시판이 있는데, 검색 결과에 나오면 그대로 저장한다. **링크의 ID 값만 보면 되므로 가장 적은 비용으로 붙일 수 있는 준수 조치다** |
| **2** | **HTTP 상태 확인** | ✅ 실측: 갤러리형 수집기에 상태 코드를 보는 코드가 **0건**이다. 차단(403/429)이 와도 "결과 0건 → 중단"으로 조용히 끝나 **막힌 것과 글이 없는 것을 구별하지 못한다.** 준수 조치이자 기능 결함이다 |
| **3** | **요청 간격 정비** | ✅ 실측: 갤러리형은 페이지마다 **고정 3초 대기**가 전부다(`waitForTimeout(3_000)`). 무작위 간격도, 키워드 전환 시 추가 간격도 없다. 게시판형에는 이미 무작위 간격이 있으니 그 방식을 옮기면 된다 |
| 4 | robots.txt 처리 | ✅ 실측: 저장소 전체에 관련 코드 **0건**. 시작 시 받아 캐시하고 요청 전 대조하는 구조가 필요하다. `Crawl-delay`를 간격에 반영하는 로직도 없다(간격이 전부 코드 상수) |
| 5 | 429/503 백오프·재시도 | 없다. 2번과 함께 넣는 것이 자연스럽다 |
| 6 | UA 신원 표기 | 둘 다 실제 브라우저 UA를 흉내 낸다. 다만 다음 카페는 모바일 UA로 화면 분기가 갈리므로 실측이 필요하다 |
| 7 | 보유기간·원문 삭제 | 관련 코드 0건. "보유기간을 정하고 지난 원문은 지운다"는 미구현이다 |
| 8 | 일일 누적 상한 | 누적 브레이크는 X에만 있다. 커뮤니티 두 곳은 회당 상한만 있다 |
| 9 | 최소수집 | 다음 카페는 작성자 닉네임을 저장한다. 화면에서 안 쓴다면 빼는 것이 가장 쉬운 조치다 |

> **판단: 1~3번은 각각 파일 한 곳 수정 수준인데, 수집량의 최대 덩어리를 차지하는 구간의
> 규정 리스크와 운영 가시성을 동시에 개선한다. 공식 API 교체 어느 것보다도 투입 대비 효과가 크다.**
> 자격증명이나 외부 승인에 전혀 의존하지 않아, **지금 당장 끝낼 수 있는 유일한 항목**이기도 하다.

**2026-08-29 결정으로 기준이 바뀌었다.** 원래는 수집량 비중으로 순서를 잡았는데, 위반 경로를 전부 끈 지금은
**심각 이슈 탐지 공백을 얼마나 빨리 메우느냐**가 기준이다.

| **1** | **앱스토어 + 구글플레이** | **10** (32%) | 자격증명만 | 심각 밀도가 가장 높은데(부정 73%·58%) **외부 심사가 없다.** 가장 빨리 메울 수 있는 구멍 |
| **2** | **커뮤니티 A 완화 3건** | — | 없음 | 유일하게 켜져 있는 커뮤니티다. **지금 막혀도 그 사실조차 모른다**(HTTP 상태를 안 본다) |
| **3** | **X** | 6 (19%) | 결제수단 | 코드는 이미 있다. 토큰만 있으면 삭제 작업. 다만 **유일하게 돈이 든다** |
| **4** | **Threads** | 1 (3%) | 비즈니스 인증 + 앱 심사 | 리드타임 최장, 얻는 것 최소. **절차만 지금 걸어 두고 코드는 마지막** |
| — | **다음 카페** | 0 | 법무 판단 | 🔴 **약관 저장 조항 판단 전까지 착수 안 함.** 현재 수집량 0이라 서두를 이유도 없다 |
| — | **커뮤니티 B** | 10 | 운영진 서면 허가 | ❌ 공식 API 없음. 방침을 바꾸거나 허가를 받는 경우에만 |

**0단계(절차 착수)는 전부 지금 동시에 건다.** 리드타임이 개발 손 밖에 있어서, 늦게 걸수록 순서와 무관하게 밀린다.

### 1 — 앱스토어 + 구글플레이

앱스토어가 **교체가 가장 깨끗하다**(필드 손실 없음, 새 의존성 없음, 파일 2개). 여기서 만드는 JWT 유틸 경험이
구글플레이의 토큰 발급으로 이어진다(알고리즘은 다르지만 `node:crypto`만 쓰는 접근은 동일).
그래서 앱스토어를 먼저 하고 구글플레이를 잇는다.

착수 전 결정 2건:
- 앱스토어: 기존 데이터 재적재를 어떻게 처리할지
- 구글플레이: 국가 루프 제거가 상한 정의·총량 추산·대시보드 카드·국가 칩 필터까지 연쇄로 이어진다.
  **화면 파급이 가장 넓다.** "현재 국가 루프가 잡던 리뷰가 전역 풀에 포함되는지" 한 번 실측할 것

### 2 — 커뮤니티 A 완화 3건

[4절](#4-교체-불가로-남는-구간--코드로-할-수-있는-완화-조치)의 1~3번. 자격증명도 외부 승인도 필요 없어
**언제든 끼워 넣을 수 있다.** 1번 작업이 자격증명 대기로 막히면 이걸 먼저 한다.

### 3 — X

토큰만 확보되면 나머지는 삭제 작업이다. 배포판은 이미 API 경로로 돌고 있어 검증 부담도 작다.
착수 전 결정 2건: 긴 글 본문 필드를 추가할지, 상한 기본값을 꺼짐으로 내릴지.

### 4 — Threads

**승인 이후에만 켠다.** 승인 전에 켜면 화면에 0건이 뜨는데, 그 0건의 원인이 "언급이 없어서"가 아니라
"권한이 없어서"다. 더구나 미승인 상태에서도 오류가 아니라 정상 응답에 축소된 결과가 오는 것으로
문서상 읽히므로 **API 응답만으로는 미승인 상태를 판별할 수 없을 가능성이 높다.**
승인 여부를 설정값으로 사람이 표시하게 두는 편이 확실하다.

## 6. 붙잡고 갈 다섯 문장

1. **전면 교체는 불가능하다.** 수집량의 절반 이상은 공식 API가 존재하지 않는다.
2. **다음 카페 API 전환은 약관 리스크를 없애는 것이 아니라 새로 만든다.** 법무 판단이 선행이다.
   같은 질문이 현재 운영 중인 네이버에도 적용되는데, 아직 확인하지 못했다.
3. **앱스토어·Threads는 기존 데이터와의 중복 판정이 확정적으로 끊긴다.** 교체 전에 방침을 정해야 한다.
4. **구글플레이는 7일 창이 최대 손실이다.** 과거분은 Play Console CSV로 채우고 이후를 API로 잇는다.
5. **투자 대비 효과가 가장 큰 작업은 API 교체가 아니라**, 남는 구간의
   차단 목록 필터·HTTP 상태 확인·요청 간격 정비다.
