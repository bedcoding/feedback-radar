## 2. 적법성 근거

### 2-1. robots.txt 실측

세 호스트를 2026-08-29에 직접 받았다. 아래는 **원문 그대로**다.

#### (a) `https://cafe.daum.net/robots.txt` — HTTP 200 — **전문**

```
User-agent: *
Allow: /_c21_/home
Allow: /_c21_/bbs_search_read
Allow: /_c21_/bbs_list
Allow: /_c21_/bbs_read

Disallow: /_c21_/
```

**우리 경로가 걸리는가: 걸리지 않는다. 그 반대다.**

이 파일은 `/_c21_/`를 통째로 막으면서, 그 안에서 **네 경로만 예외로 열어 뒀다.**
그중 두 개가 정확히 우리가 하려는 일이다.

| Allow 항목 | 무엇 | 우리 대응 동작 |
|---|---|---|
| `bbs_list` | 게시판 **글 목록** | `parseList()` — 목록에서 글을 뽑는다 |
| `bbs_read` | 게시판 **글 읽기** | `parseBody()` — 제목이 걸린 글의 본문을 읽는다 |

즉 사이트가 "봇이 게시판 목록과 글을 읽는 것"을 **거부한 것이 아니라 명시적으로 허용**했다.
robots.txt에서 이보다 강한 형태의 허용 표시는 없다. 침묵(파일 없음)이나 `Allow: /`(전체 개방)와 달리,
**차단 규칙 안에서 우리 동작만 골라 예외로 뚫어 준 형태**이기 때문이다.

#### (b) `https://m.cafe.daum.net/robots.txt` — HTTP 200 — **전문**

```
User-agent: *

Disallow: /_agreement
Disallow: /_allCafes
Disallow: /_favoriteCafes
Disallow: /_favoriteFolders
Disallow: /_makeCafe
Disallow: /_myAlimis
Disallow: /_myCafe
Disallow: /_ranking
Disallow: /_redirect
Disallow: /_search
Disallow: /_static
```

**우리 경로가 걸리는가: 걸리지 않는다.**

우리가 실제로 요청하는 것은 두 형태다.

| 요청 경로 | 위 Disallow 11줄 중 매칭되는 것 |
|---|---|
| `https://m.cafe.daum.net/{카페}/{게시판}` | 없음 |
| `https://m.cafe.daum.net/{카페}/{게시판}/{글번호}` | 없음 |

차단된 11줄은 **전부 루트 바로 아래의 `/_`로 시작하는 내부 기능 경로**다(약관, 전체 카페 목록,
즐겨찾기, 카페 만들기, 알림, 내 카페, 랭킹, 리다이렉트, 검색, 정적 리소스).
robots.txt의 경로 매칭은 루트부터의 접두사 비교이므로([RFC 9309](https://www.rfc-editor.org/rfc/rfc9309.html)),
카페 아이디가 앞에 붙는 `/{카페}/...`는 이 중 어느 줄에도 매칭되지 않는다.

> ⚠️ 한 가지 주의. `Disallow: /_search`가 있으므로 **모바일 카페 검색 기능은 쓰면 안 된다.**
> 현재 수집기는 검색을 쓰지 않고 게시판 목록만 훑는다. 나중에 "카페 안에서 키워드 검색"을
> 붙이고 싶어지면 그때 이 줄에 걸린다. 지금 목록 훑기 방식이 robots.txt 관점에서
> 더 안전한 이유이기도 하다.

#### (c) 우리가 요청하지 않는 호스트

`https://www.daum.net/robots.txt`도 HTTP 200이지만, 이 수집기는 포털 최상위를 요청하지 않는다
([적법성 문서 부록](../data-collection-compliance.md#부록-실측-원본-2026-08-29)).

#### 재확인 명령

```bash
for u in https://cafe.daum.net/robots.txt https://m.cafe.daum.net/robots.txt; do
  echo "=== $u ==="; curl -s -m 20 -w "\n[HTTP %{http_code}]\n" -A "Mozilla/5.0" "$u"
done
```

`bbs_list`·`bbs_read` 두 줄이 `Allow`에서 사라지면 이 문서의 판정이 바뀐다. 6개월마다 돌린다.

> 기타의 방법으로 사용하는 것"** 자체를 금지 대상으로 적고 있다. 법무 검토 항목에 함께 올려야 한다.

### 2-3. 판정과 근거

#### 🟢 경로 (1) 모바일 웹 직접 파싱 — 근거 있음

[적법성 문서 2절](../data-collection-compliance.md#2-무엇을-기준으로-판단했나)의 4개 층위로 나눠 본다.

| 층위 | 판정 | 근거 |
|---|---|---|
| 1. robots.txt | 🟢 **명시적 허용** | `bbs_list`·`bbs_read`가 `Allow`. 모바일 차단 목록에 우리 경로 없음 ([2-1](#2-1-robotstxt-실측)) |
| 2. 약관 | 🟡 **적용 여부 미확정** | 동의 절차를 거친 적이 없다. 다만 인적·물적 범위를 확인하지 못했다 ([2-2b](#b-경로-1에-적용될-수-있는-것--카카오-통합서비스약관)) |
| 3. 기술적 보호조치 우회 | 🟢 **해당 없음** | 로그인 세션을 쓰지 않는다. 쿠키·캡차 우회·지문 위조·IP 로테이션 없음. **403이 3회 반복되면 그 게시판의 본문 요청을 스스로 멈춘다**(`FORBIDDEN_GIVE_UP`) |
| 4. 수집 후 이용 | 🟡 **조건부** | 외부 미공개, 원문 링크 병기, 키워드 필터. 다만 본문을 800자까지 저장하고 작성자 닉네임을 저장한다 |

**층위 3이 이 경로의 가장 강한 방어선이다.** [야놀자 형사 사건(대법원 2021도1533)](../data-collection-compliance.md#국내-판례가-그은-선)이
무죄 근거로 든 조건 — "회원 가입 없이 자유롭게 접근 가능, 별도 보호조치 없음" — 에 그대로 해당한다.
그리고 **거부 신호(403)를 우회하지 않고 물러서는 코드가 실제로 들어 있다.**
[잡코리아 사건](../data-collection-compliance.md#국내-판례가-그은-선)에서 VPN으로 IP 차단을 뚫은 것이
불리하게 작용한 것과 정반대 방향이다.

#### 🟠 경로 (2) 카카오 검색 API — 이쪽이 **리스크를 만든다**

**핵심.** 이 도구는 수집물을 `items` 표에 **영구 적재하고 갱신하지 않는다.** 코드 사실이다.

[`../../packages/core/src/store.ts:236`](../../packages/core/src/store.ts)

```
INSERT INTO ..."items" (source, source_id, url, author, content, rating, posted_at,
  collected_at, keyword, service, country) VALUES ...
ON CONFLICT (source, source_id) DO NOTHING
```

`ON CONFLICT (source, source_id) **DO NOTHING**`이다. `DO UPDATE`가 아니다.

- 같은 글이 다시 들어오면 **아무것도 하지 않고 버린다.** 원문이 수정돼도 우리 쪽 사본은 안 바뀐다.
- 원문이 삭제돼도 우리 쪽 사본은 남는다. **삭제를 반영하는 코드가 저장소 전체에 없다.**
- 보유기간 정책도 원문 삭제 배치도 없다([전환 계획 4절](../official-api-migration.md#4-교체-불가로-남는-구간--코드로-할-수-있는-완화-조치) 7번 항목, "관련 코드 0건").

이 사실을 20호 원문과 나란히 놓는다.

| 20호가 금지하는 것 | 이 도구가 실제로 하는 것 |
|---|---|
| 카카오에서 받은 데이터를 **캐시 후 최신 데이터로 유지하지 않는 행위** | `DO NOTHING` — **한 번 넣으면 다시는 갱신하지 않는다** |
| **사용자 환경 개선 목적 외**의 캐시 | VOC 모니터링·집계·LLM 분류. 앱 사용자에게 보여주는 캐시가 아니다 |

**조항 후단에 정면으로 걸린다.** 그리고 30호는 "얻은 정보를 사전 승낙 없이 복사·복제"를 별도로 금지한다.

**그래서 결론이 뒤집힌다.**

> 경로 (1)에서는 **저장 방식에 대한 계약상 제약이 아예 없다.** 동의한 계약이 없기 때문이다.
> 경로 (2)로 옮기는 순간, **REST API 키를 발급받는 행위가 곧 운영정책 동의**이므로,
> 지금 열려 있던 층위가 **명시적 금지 조항 안으로 들어간다.**
>
> **"공식 API를 쓰면 안전하다"가 여기서는 성립하지 않는다.** 이 저장소에서 확인된 유일한 반례이고,
> [적법성 문서 9절 미결 항목 4번](../data-collection-compliance.md#9-미결-항목-법무-검토-요청)으로 올라가 있다.

**교정 방법이 없지는 않다.** 20호를 피하려면 `DO NOTHING`을 `DO UPDATE`로 바꾸고 주기적으로 재조회해
최신 상태를 유지해야 한다. 그러면 **수집 비용이 매번 전량 재조회로 늘고, 원문 수정 이력이 사라지고,
`collected_at` 기반 집계가 흔들린다.** 즉 조항을 지키려면 이 도구의 저장 모델을 바꿔야 한다.
**법무 판단이 "걸린다"로 나오면 전환은 진행하지 않는 것이 맞다** —
현재 수집량이 0이라 서두를 이유도 없다.

#### 부수적으로: API가 "천장을 없애 준다"도 사실이 아니다

경로 (1)의 게시판당 20건 상한이 답답해서 API를 보는 것이라면, **다른 천장으로 바뀔 뿐이다.**
공식 문서의 응답 예제가 이것을 그대로 보여준다([4-5](#4-5-상한쿼터페이지네이션) 참고).

```
"meta": { "is_end": false, "pageable_count": 983, "total_count": 218662 }
```

`total_count`는 218,662인데 **실제로 넘겨받을 수 있는 것(`pageable_count`)은 983건**이다.
문서가 `pageable_count`를 "`total_count` 중 **노출 가능** 문서 수"로 정의한다.
**키워드당 1,000건 근처에서 막힌다.** 게다가 특정 카페만 골라 볼 수 없으므로,
그 1,000건 안에 우리가 보고 싶은 카페의 글이 몇 건 들어 있을지는 보장되지 않는다.

### 3-1. 경로 (1) 모바일 웹 — 청구서가 없고, 대신 사람 손이 든다

**돈이 안 드는 이유는 살 것이 없어서다.** 발급받을 키, 등록할 결제수단, 통과할 심사,
연간 갱신할 멤버십이 하나도 없다([4-1](#4-1-사전-준비-사람이-해야-하는-것)).
같은 저장소의 앱스토어(Apple 99 USD/년)·구글플레이(US$25 일회성)와 달리
**이 경로에는 "이미 낸 돈"조차 없다**([`../api-costs.md` 1절](../api-costs.md#1-경로별-가격)).

**구동 자원도 거의 안 든다.** 이 경로는 헤드리스 브라우저가 필요 없다 —
목록 데이터가 HTML에 인라인돼 있어 **HTTP 요청 + 정규식**으로 끝난다([4-3](#4-3-엔드포인트와-요청)).
Playwright/Chromium을 띄우는 수집기와 달리 메모리·CPU 비용이 사실상 없다.
드는 것은 **실행 시간**이다.

| 자원 항목 | 값 | 출처 |
|---|---|---|
| 회당 요청 수 | **최대 40회** (목록 10 + 본문 30, 게시판 10곳 기준) | [4-5](#4-5-상한쿼터페이지네이션) |
| 회당 소요 시간 | **약 106초** (요청 간격이 대부분) | [4-5](#4-5-상한쿼터페이지네이션) |
| 브라우저 구동 | **없음** | [4-3](#4-3-엔드포인트와-요청) |
| 저장 용량 | 글당 최대 800자 | [4-5](#4-5-상한쿼터페이지네이션) |

#### 무료 대신 걸리는 것 — 쿼터가 아니라 **물리적 상한**이다

계정이 없으니 계정 쿼터도 없다. 그 자리를 서버·코드 상한이 대신한다. **전부 숫자다.**

| 상한 | 값 | 넘길 수 있나 |
|---|---|---|
| **게시판당 글 수** | **20건** | ❌ 서버가 정한다. `?page=2`가 무시된다 |
| **게시판 개수** | **최대 10개** | 설정 검증기. 코드 수정 필요 |
| **본문 조회** | **회당 30건** (실행 전체 합계) | 코드 수정 |
| **본문 길이** | **800자** | 코드 수정 |
| **403 포기** | **3회** | 의도된 동작 |
| **일일/월간 쿼터** | **없다** | 대신 차단당할 수 있다 |

⚠️ **20건 상한이 곧 기회비용이다.** 종합 게시판은 20건이 **1~2분 분량**(실측 분당 19건)이라
6시간 주기에서 **99% 이상을 못 본다**([4-6 함정 3](#4-6-함정)). 돈을 더 내서 풀 수 있는 상한이 아니다.
**과거 글에는 이 경로로 아예 닿을 수 없다.**

#### 차단 리스크가 비용이다

| 리스크 | 지금 코드의 동작 | 비용의 형태 |
|---|---|---|
| 403 3회 | 그 게시판 본문 요청을 **스스로 멈춘다**(`FORBIDDEN_GIVE_UP`) | 이후 **제목만 저장** → LLM 분류 정확도 하락 |
| 429·503 | **백오프·재시도가 없다.** 그 게시판을 건너뛰고 계속 간다 | 조용한 누락 ([4-6 함정 14](#4-6-함정)) |
| IP 차단 | **우회하지 않는다** (VPN·프록시·IP 로테이션 없음) | 수집이 0건이 된다. **그래도 우회는 하지 않는다** — 층위 3 방어선이 사라진다([2-3](#2-3-판정과-근거)) |

> 🟢 이 "물러서는 비용"은 감수하는 것이 맞다. 우회 코드를 넣는 순간
> [잡코리아 사건](../data-collection-compliance.md#국내-판례가-그은-선)과 같은 자리에 선다.
> **차단당하는 것이 비용이 아니라, 뚫는 것이 비용이다.**

#### 유지보수가 진짜 비용이다 — 공식 스펙이 없어서 예고 없이 깨진다

계약도 버전 관리도 없는 HTML을 읽는다. **다음이 화면을 바꾸면 그날 조용히 깨진다.**
아래 넷은 전부 **에러가 안 나고 데이터만 비는** 형태라, 사람이 눈으로 찾아야 한다.

| 깨지는 지점 | 무엇이 바뀌면 | 증상 |
|---|---|---|
| UA 기반 모바일 판별 | 다음이 UA 처리를 바꾸면 | **HTTP 200에 0건** ([함정 2](#4-6-함정)) |
| 상대 시각 표기 | `3분 전`·`26.08.20` 표기가 바뀌면 | `postedAt`이 `undefined` ([함정 8](#4-6-함정)) |
| 본문 끝 마커 (`foot_content`·`cmtWrap`·`view_cmt`) | 마커 이름이 바뀌면 | **본문이 빈 문자열** ([함정 9](#4-6-함정)) |
| 화면 부품 문구 제거 목록 (**하드코딩**) | 버튼 문구가 늘거나 바뀌면 | 본문에 `북마크`·`공유하기`가 섞임 ([함정 10](#4-6-함정)) |

**정기적으로 사람이 내야 하는 비용:**

| 주기 | 할 일 | 누가 |
|---|---|---|
| **6개월** | robots.txt 재확인 — `bbs_list`·`bbs_read`가 `Allow`에서 사라지면 판정이 바뀐다 ([2-1](#2-1-robotstxt-실측)) | 개발 |
| 붙일 때 1회 | 게시판 선정 — **개발이 정할 수 없다.** 업종·서비스마다 다르다 | **기획/운영** |
| 붙일 때 1회 | 게시판마다 **비로그인으로 열리는지** 실측(`grep -c 'articles.push'`). 건너뛰면 조용히 0건 | 기획/운영 |
| 상시 | "작성일 없음" 필터 모니터링 — 시각 표기 변경 조기 감지 | 운영 |

> 🔴 **운영진 허가를 받는 경로는 없고, 만들어서도 안 된다.** 비공개 게시판을 보려고
> **가입·등업해서 로그인 세션으로 긁는 것은 금지**다([4-1](#4-1-사전-준비-사람이-해야-하는-것)).
> 그 순간 층위 3(기술적 보호조치 우회)에 걸려 이 소스의 가장 강한 방어 논거가 사라진다.
> **비로그인으로 안 열리는 게시판의 "허가 비용"은 협상이 아니라 포기다.**

> 참고: 현재 누적 수집량이 **0건**이므로([1절](#1-현황)) **지금까지 실제로 지불된 비용도 0이다.**
> 반대로 효용도 0이다. 비용 판단은 "켠 뒤에 얼마나 드나"로 해야 한다.

### 3-2. 경로 (2) 카카오 Daum 검색 API — **무료지만 지금은 쓸 수 없다**

#### 돈 대신 걸리는 것 — 쿼터 (전부 숫자)

| 쿼터 | 값 | 우리 규모 | 출처 |

| **Daum 검색 전체 일간** | **50,000건** | 🟢 여유 | ✅ 같은 문서 |
| **전체 API 월간** | **3,000,000건** | 🟢 여유 | ✅ 같은 문서 |
| **요청 길이** | 30초 이내 (Hard) | 🟢 | ✅ 운영정책 제6조 |
| **일일 총 API 호출** | 1,000만 건 초과 시 Hard 제한 | 🟢 | ✅ 운영정책 제6조 |

산출 근거: 키워드 9개 × 20페이지 = 회당 180 요청, 6시간 주기(하루 4회) → **하루 720건**([4-5](#4-5-상한쿼터페이지네이션)).
**쿼터가 이 도구의 제약이 되는 일은 없다.**

> 🟠 **쿼터 초과는 단순 기술적 한도가 아니라 계약 위반이다.** 운영정책 제5조 31호가
> "제6조에 따라 정한 제공 한도를 초과하여 서비스를 이용하는 행위"를 **금지 행동**으로 적는다([함정 I](#4-6-함정)).

#### 🔴 그런데 무료인 것이 의미가 없다 — 지금은 쓸 수 없기 때문이다

**이 소스의 비용 절에서 가장 중요한 문장이다.**

> **가격이 0원이어도 이 API는 지금 켤 수 없다.** 운영정책 **제5조 20호·30호**가
> 이 도구의 `ON CONFLICT DO NOTHING` 영구 적재 방식에 걸릴 수 있고,
> **REST API 키를 발급받는 행위 자체가 그 정책에 동의하는 것**이기 때문이다([2-3](#2-3-판정과-근거)).
> 경로 (1)에는 없던 계약상 제약이 **무료 API를 켜는 순간 새로 생긴다.**

**그래서 이 경로의 실제 비용은 돈이 아니라 절차와 개발 공수다.**

| 비용 항목 | 내용 | 누가 |
|---|---|---|
| 🔴 **법무 검토** | 20호·30호에 영구 적재가 걸리는지 판단. **여기가 통과되기 전에는 착수하지 않는다** | **법무** |
| **저장 모델 변경** | 20호를 피하려면 `DO NOTHING` → `DO UPDATE` + 주기적 재조회. 그러면 **수집 비용이 매번 전량 재조회로 늘고**, 원문 수정 이력이 사라지고, `collected_at` 기반 집계가 흔들린다 | 개발 |
| **기능 재구현** | 카페 지정 파라미터가 없어 `cafename` 사후 필터·`sourceId` 정규화·`<b>` 제거를 새로 만들어야 한다 | 개발 |
| **잃는 것** | `author` 필드, 본문 전문 → 스니펫 ([4-4](#4-4-응답--rawitem-매핑)) | — |

> 🟡 **서두를 이유가 없다.** 현재 수집량이 0건이고 경로 (1)이 무료로 돌아간다.
> **법무 판단이 "걸린다"로 나오면 전환은 하지 않는 것이 맞다**([2-3](#2-3-판정과-근거)).

## 4. 연동 방법

**두 경로를 모두 적는다.** 4-1 ~ 4-6 안에서 경로별로 나눠 쓴다.
**권장은 경로 (1)이다.** 경로 (2)는 [2-3](#2-3-판정과-근거)의 법무 판단이 "문제없음"으로 나온 뒤에만 착수한다.

### 4-1. 사전 준비 (사람이 해야 하는 것)

#### 경로 (1) 모바일 웹 — 사람이 할 일이 사실상 없다

| # | 할 일 | 누가 | 비고 |
|---|---|---|---|
| 1 | 볼 게시판을 고른다 | **기획/운영** | 개발이 정할 수 없다. 업종·서비스마다 다르다 |
| 2 | 고른 게시판의 `카페아이디/게시판아이디`를 알아낸다 | 기획/운영 | 아래 방법 |
| 3 | 각 게시판이 **비로그인으로 열리는지** 확인한다 | 기획/운영 | 아래 방법. **이 단계를 건너뛰면 조용히 0건이 된다** |
| 4 | 화면 설정에 넣고 소스를 켠다 | 누구나 | 대시보드 → 수집 상한 → 다음 카페 |

**발급받을 키가 없고, 승인받을 사람이 없고, 결제수단이 필요 없다.**
자격증명이 계정별로 갈리는 앱 리뷰 쪽 전환과 정반대다.

**아이디 알아내는 법.** 브라우저에서 게시판을 연 뒤 주소를 본다.

```
https://cafe.daum.net/{카페아이디}/{게시판아이디}          ← 데스크톱
https://m.cafe.daum.net/{카페아이디}/{게시판아이디}        ← 모바일 (수집기가 쓰는 것)
```

설정에 넣는 값은 슬래시로 이은 한 줄이다: `{카페아이디}/{게시판아이디}`

**형식 규칙**(검증기가 막는다 — [`../../packages/core/src/paths.ts:536`](../../packages/core/src/paths.ts)):

| 항목 | 규칙 | 틀리면 |
|---|---|---|
| 카페아이디 | `[a-z0-9_-]` 2~40자. **소문자만** | 저장 시 오류 메시지 |
| 게시판아이디 | `[A-Za-z0-9_]` 2~12자. **대소문자를 구분한다** | 저장 시 오류 메시지 |
| 개수 | 최대 **10개** | 저장 시 오류 메시지 |

> ⚠️ **게시판아이디를 소문자로 내리면 안 된다.** 실측한 값들이 대소문자를 섞어 쓴다(`9fQk` 같은 형태).
> 검증기가 대소문자를 보존하는 이유다.

**게시판이 비로그인으로 열리는지 확인하는 법** (설정에 넣기 전에 반드시 한다):

```bash
UA='Mozilla/5.0 (iPhone; CPU iPhone OS 17_5 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/17.5 Mobile/15E148 Safari/604.1'
curl -s -A "$UA" -H 'Accept-Language: ko-KR,ko;q=0.9' \
  "https://m.cafe.daum.net/{카페}/{게시판}" | grep -c 'articles.push'
```

| 결과 | 뜻 | 조치 |
|---|---|---|
| **1 이상** | 비로그인으로 목록이 열린다 | 넣어도 된다 |
| **0** | 비공개 게시판이거나, 아이디가 틀렸거나, 구조가 바뀌었다 | 넣으면 조용히 0건이 된다 |

> 🔴 **가입·등업해서 로그인 세션으로 긁는 것은 하면 안 된다.** 그 순간
> [층위 3](../data-collection-compliance.md#2-무엇을-기준으로-판단했나)에 걸리고, 이 소스의 가장 강한
> 방어 논거가 사라진다. **비로그인으로 안 열리는 게시판은 그냥 포기한다.**

> ⚠️ **게시판 성격을 골라야 한다.** 이 경로는 **게시판당 최신 20건이 물리적 상한**이다.
> 글이 몰리는 종합 게시판은 20건이 **1~2분 분량**이라(코드 주석의 실측: 분당 19건)
> 수집 주기를 아무리 줄여도 대부분을 놓친다. **주제별 게시판은 20건이 며칠~몇 주를 덮는다**
> (실측: 11일, 25일). **후자를 골라야 한다.**

### 4-2. 인증

#### 경로 (1) — 인증이 없다

토큰도 키도 쿠키도 없다. **보내는 것은 헤더 두 개뿐**이다
([`daum-cafe.ts` `fetchText()`](../../apps/pipeline/src/collectors/daum-cafe.ts)).

```
User-Agent: Mozilla/5.0 (iPhone; CPU iPhone OS 17_5 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/17.5 Mobile/15E148 Safari/604.1
Accept-Language: ko-KR,ko;q=0.9
```

**UA가 기능상 필수다.** 데스크톱 UA를 보내면 데스크톱 화면으로 밀리고, 데스크톱은
비로그인에게 목록을 주지 않는다(HTTP 200에 88KB를 돌려주면서 글 링크가 0건이고
`MEMBER_ROLENAME: "비회원"`만 들어 있다 — 코드 주석의 2026-08 실측, 게시판 7개 전부).
**즉 UA를 바꾸면 오류 없이 0건이 된다.** [4-6](#4-6-함정) 참고.

> 🟡 **"합법적 크롤링"의 통상적 예절은 신원을 밝히는 것**인데, 지금은 실제 브라우저 UA를 그대로
> 흉내 낸다. 모바일 판별을 깨지 않으면서 신원을 붙이는 형태가 제안돼 있다
> ([적법성 문서 7-3](../data-collection-compliance.md#7-3-user-agent에-신원을-밝힌다)).
>
> ```
> Mozilla/5.0 (iPhone; ...) Safari/604.1 FeedbackRadar/1.0 (+연락처)
> ```
>
> ⚠️ **다음이 이 UA에도 모바일 페이지를 계속 주는지는 확인하지 못했다.** 바꾸기 전에
> 위 `grep -c 'articles.push'` 명령으로 실측할 것. **이걸 안 하고 바꾸면 조용히 0건이 된다.**

#### 경로 (2) — 정적 REST API 키

✅ **공식 문서 원문**(<https://developers.kakao.com/docs/ko/daum-search/dev-guide>):

| 이름 | 설명 | 필수 |
|---|---|---|
| `Authorization` | `Authorization: KakaoAK ${REST_API_KEY}` — 인증 방식, 서비스 앱에서 REST API 키로 인증 요청 | O |

```
Authorization: KakaoAK 1234567890abcdef1234567890abcdef
```

- **토큰 수명**: 액세스 토큰이 아니라 **앱 고정 키**다. OAuth 흐름도, 만료도, 갱신 루프도 없다.
  이 저장소의 다른 회전 자격증명(Threads 60일, 구글플레이 1시간)과 달리 새 설계가 필요 없다.
- ⚠️ **확인 필요**: 키 재발급(rotate) 절차와, 재발급 시 기존 키가 언제 무효화되는지는
  이번 조사에서 확인하지 못했다. 콘솔의 [앱 키] 화면에서 확인해야 한다.
- 🔴 **키를 저장소에 커밋하지 않는다.** 운영정책 제5조 30호가 "비밀 키, 엑세스 토큰"을
  사전 승낙 없이 타인에게 제공하는 것을 명시적으로 금지한다. 환경변수로만 다룬다.

### 4-3. 엔드포인트와 요청

#### 경로 (1) 모바일 웹 — 요청 두 종류

**① 게시판 목록**

```
GET https://m.cafe.daum.net/{카페아이디}/{게시판아이디}
```

파라미터 없음. **`?page=2`는 무시된다**(같은 20건을 돌려준다). 페이지를 넘길 수 없다.

응답은 HTML이지만 **브라우저가 필요 없다.** 목록이 Vue로 렌더돼 `<a href>`는 `javascript:`지만,
그 데이터가 HTML에 인라인돼 있다.

```
articles.push({ dataid: Number("41"), fldid: "AbCd", title: "글 제목",
                writerNickname: "닉네임", articleElapsedTime: "3분 전", ... });
```

정규식 `/articles\.push\(\{[\s\S]*?\}\);/g`로 블록을 잡고, 필드는
`/{이름}:\s*(?:Number\()?"?([^",\n)]*)/`로 뽑는다(값이 `Number("41")`로도 `"제목"`으로도 온다).

**② 글 본문** — 제목에 키워드가 걸린 글만

```
GET https://m.cafe.daum.net/{카페아이디}/{fldid}/{dataid}
```

> ⚠️ **`{게시판아이디}`가 아니라 데이터의 `fldid`를 쓴다.** 전체글보기 경로는 여러 게시판의 글을
> 섞어 내려주므로, 요청한 게시판 이름을 그대로 쓰면 URL이 틀린다.

본문은 `class="tx-content-container"`(다음 에디터 컨테이너) 안에 있다.

**예시 요청** (그대로 붙여 넣어 확인할 수 있다):

```bash
UA='Mozilla/5.0 (iPhone; CPU iPhone OS 17_5 like Mac OS X) AppleWebKit/605.1.15 (KHTML, like Gecko) Version/17.5 Mobile/15E148 Safari/604.1'
curl -s -A "$UA" -H 'Accept-Language: ko-KR,ko;q=0.9' \
  "https://m.cafe.daum.net/{카페}/{게시판}" \
  | grep -o 'articles\.push({[^}]*}' | head -3
```

#### 경로 (2) 카카오 API

```
GET https://dapi.kakao.com/v2/search/cafe
```

✅ **쿼리 파라미터 (공식 문서 원문):**

| 이름 | 타입 | 설명 | 필수 |
|---|---|---|---|
| `query` | String | 검색을 원하는 질의어 | **O** |
| `sort` | String | 결과 문서 정렬 방식, `accuracy`(정확도순) 또는 `recency`(최신순) 중 하나(기본값: `accuracy`) | X |
| `page` | Integer | 결과 페이지 번호, 1~50 사이의 값(기본값: `1`) | X |
| `size` | Integer | 한 페이지에 보여질 문서 수, 1~50 사이의 값(기본값: `10`) | X |

🔴 **`sort=recency`를 반드시 명시한다.** 기본값이 `accuracy`(정확도순)라서, 지정하지 않으면
**몇 년 전 인기 글이 최신 글보다 위에 온다.** 공식 문서의 응답 예제가 그 증거다 —
아무 조건 없이 부른 결과의 첫 문서 `datetime`이 `2017-01-31T16:57:33.000+09:00`이다.
불만·사건 모니터링이 용도인 이 도구에서 이건 치명적이다. → [4-6](#4-6-함정)

**예시 요청 (공식 문서 원문):**

```bash
curl -v -G GET "https://dapi.kakao.com/v2/search/cafe" \
  --data-urlencode "query=아이유" \
  -H "Authorization: KakaoAK ${REST_API_KEY}"
```

**이 도구가 실제로 보낼 형태:**

```bash
curl -s -G "https://dapi.kakao.com/v2/search/cafe" \
  --data-urlencode "query={키워드}" \
  --data-urlencode "sort=recency" \
  --data-urlencode "size=50" \
  --data-urlencode "page=1" \
  -H "Authorization: KakaoAK ${KAKAO_REST_API_KEY}"
```

> ❌ **카페를 지정하는 파라미터가 없다.** 위 표가 파라미터의 전부다.
> 특정 카페만 보려면 응답의 `cafename`으로 **사후 필터**하는 수밖에 없다.
> 이것이 경로 (1)에 있던 기능이 경로 (2)에서 사라지는 지점이고,
> [4-6](#4-6-함정)에서 조용한 0건의 원인이 된다.

### 4-4. 응답 → RawItem 매핑

`RawItem` 정의: [`../../packages/core/src/types.ts`](../../packages/core/src/types.ts)

#### 경로 (1) 모바일 웹 → RawItem

| RawItem 필드 | 이 경로의 출처 | 비고 |
|---|---|---|
| `source` | 상수 `'daum-cafe'` | |
| `sourceId` | `` `${cafe}/${fldid}/${dataid}` `` | ⚠️ **`dataid`만 쓰면 안 된다.** 카페 안에서 유일하지 않다 — **게시판이 다르면 같은 번호가 있다.** 경로 전체를 id로 쓴다 |
| `url` | `` `https://m.cafe.daum.net/${cafe}/${fldid}/${dataid}` `` | `{게시판아이디}`가 아니라 `fldid`다 |
| `author` | 목록 데이터 `writerNickname` | 🟡 **채우지 않는 편이 낫다.** [2-4 개인정보](#개인정보-개인정보보호법) 참고. 빈 문자열이면 `undefined` |
| `content` | 본문이 있으면 `` `${title}\n${body}` ``, 없으면 `title` | 본문은 **800자 절단**. 본문 없이 제목만 저장되는 경우가 흔하다 → [4-5](#4-5-상한쿼터페이지네이션) |
| `rating` | **못 채운다** | 별점 개념이 없다 |
| `postedAt` | 목록 데이터 `articleElapsedTime` → `fromElapsedOrDate()` | ⚠️ 한 목록에 네 형식이 섞인다: `방금전`, `3분 전`, `03:58`, `26.08.20`. **아래 표 참고** |
| `keyword` | 제목에 걸린 첫 키워드(소문자) | `needles.find((n) => lower.includes(n))` |
| `service` | 호출부에서 주입 | `collectDaumCafe(..., service)` |
| `country` | **못 채운다 (비워 둔다)** | 커뮤니티에는 스토어 국가 개념이 없다. `types.ts`의 규약 |

**`postedAt` 형식별 처리** ([`../../packages/core/src/time.ts`](../../packages/core/src/time.ts)):

| 목록 표기 | 파서 | 결과 |
|---|---|---|
| `방금전` / `방금 전` | `fromElapsedOrDate` | 현재 시각 |
| `3분 전`, `2시간 전`, `5일 전` | `fromElapsedOrDate` | 현재 시각 − 경과 |
| `03:58` | `fromShortDateOrTime` | **오늘** 그 시각 |
| `26.08.20` | `fromShortDateOrTime` | 2026-08-20 (두 자리 연도는 2000년대로 읽는다) |
| `08.20` | `fromShortDateOrTime` | **올해** 8월 20일 |
| 그 외 / 못 읽음 | — | **`undefined`** → [4-6](#4-6-함정) |

#### 경로 (2) 카카오 API → RawItem

✅ **응답 `Document` 스펙 (공식 문서 원문):**

| 이름 | 타입 | 설명 |
|---|---|---|
| `title` | String | 카페 글 제목 |
| `contents` | String | 카페 글 내용중 일부 |
| `url` | String | 카페 글 URL |
| `cafename` | String | 카페 이름 |
| `thumbnail` | String | 카페 글 대표 미리보기 이미지 URL |
| `datetime` | Datetime | 카페 글 작성시간, ISO 8601 형식 `[YYYY]-[MM]-[DD]T[hh]:[mm]:[ss].000+[tz]` |

**매핑:**

| RawItem 필드 | API 응답 필드 | 비고 |
|---|---|---|
| `source` | 상수 | 경로 (1)과 **다른 값을 쓸지 정해야 한다.** 같은 `'daum-cafe'`로 두면 화면에서 두 경로가 섞여 보인다 |
| `sourceId` | `url`에서 경로 추출 | ⚠️ **응답에 글 ID 필드가 없다.** `url`을 파싱해야 한다. 공식 예제의 형태는 `http://cafe.daum.net/ok1221/9fQk/39709` — **`https`가 아니라 `http`이고, `m.` 없는 데스크톱 호스트**다. 경로 세 조각(`{카페}/{게시판}/{글번호}`)은 경로 (1)의 `sourceId`와 같은 모양이라, 파싱해서 맞추면 두 경로의 중복 판정을 이을 수 있다. **`url` 문자열을 그대로 `sourceId`로 쓰면 이어지지 않는다** |
| `url` | `url` | 위와 같은 이유로 `https`/`m.` 정규화를 할지 정해야 한다 |
| `author` | ❌ **못 채운다** | **응답에 작성자 필드가 없다.** `cafename`은 카페 이름이지 사람이 아니다. 🟢 개인정보 관점에서는 오히려 이득이다 |
| `content` | `` `${title}\n${contents}` `` | 🔴 **`<b>` 태그를 벗겨야 한다.** 공식 예제 원문이 `"연예인 무대의상 정보 가져왔어! (feat. 레드벨벳, <b>아이유</b>)"`처럼 **검색어를 `<b>`로 감싸서 준다.** → [4-6](#4-6-함정) |
| `rating` | ❌ 못 채운다 | 별점 개념 없음 |
| `postedAt` | `datetime` | 🟢 **경로 (1)보다 낫다.** ISO 8601 정시각이라 상대표기 파싱이 아예 필요 없다 |
| `keyword` | 요청에 쓴 `query` | |
| `service` | 호출부에서 주입 | |
| `country` | ❌ 비워 둔다 | |
| — | `cafename` | **RawItem에 담을 자리가 없다.** 특정 카페만 보려면 이 값으로 **저장 전에 필터**해야 한다 |
| — | `thumbnail` | 쓰지 않는다 |

**경로 (1) 대비 잃는 필드: `author` 하나, 그리고 본문이 전문 → 스니펫으로 줄어든다.**
`contents`가 얼마나 긴지는 문서에 명시가 없다(예제는 약 90자). ⚠️ **실측이 필요하다.**
본문이 LLM 분류 입력이므로 표시 문제가 아니라 **분류 정확도 문제**다.

### 4-5. 상한·쿼터·페이지네이션

#### 경로 (1) 모바일 웹

| 상한 | 값 | 어디서 | 넘길 수 있나 |
|---|---|---|---|
| **게시판당 글 수** | **20건** | 서버가 정한다 | ❌ **불가.** `?page=2`가 무시되고, 끝까지 스크롤해도 더 불러오지 않는다. 설정의 `daumCafePosts`는 `min:1 / max:20 / def:20`인데, **최대가 20인 것은 취향이 아니라 물리적 상한이다** |
| **게시판 개수** | **최대 10개** | 설정 검증기 | ❌ 코드 수정 필요 |
| **본문 조회 건수** | **회당 30건** (`MAX_BODY_FETCH`) | 코드 상수 | 코드 수정. ⚠️ **게시판별이 아니라 실행 전체 합계**다 |
| **403 포기 기준** | **3회** (`FORBIDDEN_GIVE_UP`) | 코드 상수. **게시판마다 새로 센다** | 의도된 동작(거부 신호 존중) |
| **본문 길이** | **800자** | `parseBody()` 끝의 `.slice(0, 800)` | 코드 수정 |
| **요청 간격** | 본문 조회 전 1.2~3초, 게시판 전환 후 2.5~6초. 무작위(`ms = min + Math.random()**1.8 * (max-min)`) | 코드 상수 | — |
| **쿼터** | **없다** (인증이 없으니 계정 쿼터도 없다) | | 대신 차단당할 수 있다 |
| **일일 누적 상한** | **없다** | | 회당 상한만 있다 |

**페이지네이션: 없다.** 이 경로의 본질적 한계다. 게시판 목록 요청 1회 = 최신 20건이 전부다.
**과거 글에는 이 경로로 닿을 수 없다.**

**회당 총 요청 수 추산** (게시판 10곳 기준):

```
목록 10회 + 본문 최대 30회 = 최대 40회
소요 시간 ≈ 10 × 4.25초(게시판 간격) + 30 × 2.1초(본문 간격) ≈ 106초
```

#### 경로 (2) 카카오 API

| 상한 | 값 | 출처 |
|---|---|---|
| `page` | **1~50** | ✅ 공식 문서 파라미터 표 |
| `size` | **1~50** (기본 10) | ✅ 공식 문서 파라미터 표 |
| **이론상 최대** | 50 × 50 = **2,500건/키워드** | 위 둘의 곱 |
| **실질 최대** | `pageable_count` — 공식 예제에서 **983** | ✅ 공식 문서 응답 예제 |
| **카페 검색 일간 쿼터** | **30,000건** | ✅ [쿼터 문서](https://developers.kakao.com/docs/ko/getting-started/quota) |
| **Daum 검색 전체 일간 쿼터** | **50,000건** | ✅ 같은 문서 |
| **전체 API 월간 쿼터** | **3,000,000건** | ✅ 같은 문서 |
| **요청 길이** | 30초 이내 (Hard) | ✅ 운영정책 제6조 |
| **일일 총 API 호출** | 1,000만 건 초과 시 Hard 제한 | ✅ 운영정책 제6조 |

> 쿼터 상향은 "협의 및 제휴가 필요하므로 별도 문의"라고 공식 문서가 적고 있다.
> **이 도구 규모에서는 필요 없다.** 키워드 9개 × 20페이지 = 회당 180 요청,
> 6시간 주기(하루 4회)면 하루 720건으로 **일간 쿼터 30,000건의 2.4%**다.

**페이지 넘기는 방법** — `meta.is_end`를 본다.

✅ **공식 문서의 `Meta` 정의 원문:**

| 이름 | 타입 | 설명 |
|---|---|---|
| `total_count` | Integer | 검색된 문서 수 |
| `pageable_count` | Integer | `total_count` 중 노출 가능 문서 수 |
| `is_end` | Boolean | 현재 페이지가 마지막 페이지인지 여부, 값이 `false`면 page를 증가시켜 다음 페이지를 요청할 수 있음 |

```
page = 1
while true:
    응답 = GET .../search/cafe?query=K&sort=recency&size=50&page=page
    저장(응답.documents)
    if 응답.meta.is_end: break
    if page >= 50: break          # ← page 상한. 이 줄이 없으면 51페이지에서 오류가 난다
    page += 1
```

🔴 **`if page >= 50: break`를 빠뜨리면 안 된다.** `is_end`만 믿고 돌면 `page` 상한(50)을 넘는
요청을 보내게 된다. `pageable_count`가 2,500보다 크면 `is_end`가 계속 `false`이기 때문이다.

### 4-6. 함정

**이 절이 이 문서에서 가장 중요하다. 아래는 전부 "에러 없이 0건이 되거나 잘린 데이터가 들어오는" 지점이다.**

#### 경로 (1) 모바일 웹

| # | 함정 | 무엇이 보이나 | 실제로 무슨 일이 | 어떻게 알아채나 |
|---|---|---|---|---|
| **1** | 🔴 **본문에만 키워드가 있는 글은 영원히 안 들어온다** | 수집량이 그냥 적다 | 코드가 **제목만 본다** — `if (!needles.some((n) => lower.includes(n))) continue;`. 본문은 제목이 걸린 뒤에야 읽는다. **"제목엔 없고 본문에서 자사 서비스를 욕한 글"은 구조적으로 못 본다** | 이 경로의 설계 자체다. 본문까지 보려면 게시판 전체 본문을 다 받아야 해서 요청 수가 20배가 된다. **경로 (2)는 이 구멍이 없다** |
| **2** | 🔴 **UA를 바꾸면 조용히 0건** | `글을 찾지 못했습니다` 경고 1줄 | 데스크톱 UA → 데스크톱 화면 → **HTTP 200에 88KB인데 글 링크 0건**. `MEMBER_ROLENAME: "비회원"`만 들어 있다 | UA를 건드린 뒤 `grep -c 'articles.push'`가 0이면 이것이다 |
| **3** | 🔴 **종합 게시판을 넣으면 대부분을 놓친다** | 건수는 나온다 | 게시판당 20건이 **1~2분 분량**(실측 분당 19건). 6시간 주기면 **99% 이상을 못 본다.** 오류는 하나도 안 난다 | 들어온 글의 `postedAt`이 전부 실행 직전 몇 분 안에 몰려 있으면 이것이다 |
| **4** | 🟠 **비공개 게시판** | `다음 카페({게시판}): 글을 찾지 못했습니다 (비공개 게시판이거나 구조 변경)` | 목록이 안 열린다. **경고는 나오지만 실행은 계속되고 최종 건수만 줄어든다** | 위 경고. **CollectTask의 `note`에는 안 담긴다** |
| **5** | 🟠 **게시판 아이디 대소문자** | 저장 시 오류 or 0건 | 검증기가 `[A-Za-z0-9_]`로 대소문자를 보존한다. 소문자로 바꿔 넣으면 **다른 게시판이거나 없는 게시판**이 된다 | 4번과 같은 경고 |
| **6** | 🟠 **본문 30건 상한이 실행 전체 합계** | 뒤쪽 게시판 글이 제목만 저장됨 | `MAX_BODY_FETCH`는 게시판별이 아니다. 앞 게시판이 30건을 다 쓰면 **뒤 게시판은 전부 제목만** 저장된다. 오류 없음 | 로그의 `(본문 N건 확인)`이 30이면 상한에 닿은 것이다. 저장된 `content`에 줄바꿈이 없으면 제목만인 글이다 |
| **7** | 🟠 **403 3회 후 제목만** | `글 상세가 막혀 있어 제목만 저장합니다` 1줄 | 의도된 동작(거부 신호 존중). 이후 그 게시판은 **본문 없이 제목만** 저장된다. 분류 정확도가 떨어진다 | 위 로그 1줄. 게시판마다 카운터가 리셋된다 |
| **8** | 🟠 **작성일이 `undefined`로 조용히 빠진다** | 목록에는 있는데 날짜 필터·브리핑에 안 나온다 | `fromElapsedOrDate`가 못 읽는 형식(다음이 표기를 바꾸는 등)이면 **`postedAt`이 `undefined`**가 된다. 그 글은 날짜별 브리핑과 기간 필터에서 **통째로 빠진다**([`types.ts`의 `ItemQuery.undated` 주석](../../packages/core/src/types.ts)) | 화면의 **"작성일 없음" 필터**(`undated`)로 골라 본다. 여기 갑자기 다음 카페 글이 쌓이면 표기가 바뀐 것이다 |
| **9** | 🟠 **본문 파싱이 빈 문자열** | `content`가 제목만 | 다음 에디터가 본문을 `div`로 여러 겹 감싼다(이미지 한 장에도 `figure-img` 래퍼). 첫 `</div>`에서 자르면 **이미지 위주 게시판의 본문이 전부 빈 문자열**이 된다 — 실제로 겪은 문제다. 지금 코드는 끝 마커(`foot_content`, `cmtWrap`, `view_cmt`)로 우회한다. **마커 이름이 바뀌면 다시 깨진다** | 6번과 같은 방법 |
| **10** | 🟡 **화면 부품 문구가 본문에 섞인다** | 분류가 이상해진다 | 본문 컨테이너가 버튼 영역까지 감싼다. `다음검색`, `북마크`, `공유하기`, `신고 센터로 신고`, `목록`, `댓글 N` 같은 문구가 본문에 붙는다. **모든 글에 같은 문구가 붙으면 본문 기준 중복 판정(`dropFlooding`)까지 흐려진다.** 지금 코드가 지우고 있지만 목록은 하드코딩이다 | 저장된 `content`를 눈으로 본다 |
| **11** | 🟡 **`fldid` 대신 게시판아이디를 쓰면 URL이 틀린다** | 링크가 404 | 전체글보기 경로는 여러 게시판 글을 섞어 준다. 코드는 `field(block, 'fldid') \|\| board`로 처리한다 | 저장된 `url`을 눌러 본다 |
| **12** | 🟡 **`dataid`만으로 `sourceId`를 만들면 글이 사라진다** | 건수가 적다 | `dataid`는 카페 안에서 유일하지 않다. **게시판이 다르면 같은 번호가 있다.** `ON CONFLICT DO NOTHING`이 뒤에 온 글을 조용히 버린다 | `sourceId`에 `/`가 두 개 있는지 확인 |
| **13** | 🟡 **설정 형식 오타** | `'{값}'는 '카페/게시판' 형식이 아니어서 건너뜁니다` | 조용히 버리지 않고 로그는 남긴다 ✅ | 위 로그 |
| **14** | 🟡 **네트워크 실패와 차단이 같은 모양** | `다음 카페: HTTP {상태} ({URL})` 또는 `요청 실패` | 목록 요청이 실패하면 그 게시판을 **건너뛰고 계속 간다**. 429나 503이 와도 **백오프·재시도가 없다** | 로그의 HTTP 상태. ✅ 상태 코드를 보긴 한다(다른 커뮤니티 수집기와 다른 점이다) |

#### 경로 (2) 카카오 API

| # | 함정 | 무엇이 보이나 | 실제로 무슨 일이 |
|---|---|---|---|
| **A** | 🔴 **`sort`를 안 넣으면 최신 글이 안 온다** | 건수는 정상, 내용이 옛날 글 | 기본값이 `accuracy`(정확도순)다. **공식 문서 예제 응답의 첫 문서가 2017년 글이다.** 오류가 안 나고 데이터도 그럴듯해서 **한참 뒤에나 알아챈다.** `sort=recency`를 반드시 명시한다 |
| **B** | 🔴 **`<b>` 태그가 본문에 섞여 LLM으로 간다** | 분류가 미묘하게 나빠진다 | 응답의 `title`·`contents`가 검색어를 `<b>`로 감싸서 온다(공식 예제 원문에서 확인). 벗기지 않으면 **모든 글에 같은 마크업이 붙어** 분류 입력이 오염되고 `dropFlooding` 판정도 흐려진다 |
| **C** | 🔴 **특정 카페 필터가 조용한 0건을 만든다** | 그냥 0건 | 카페 지정 파라미터가 없어 `cafename`으로 사후 필터해야 한다. 그런데 도달 가능한 것은 `pageable_count`(약 1,000건)까지다. **원하는 카페의 글이 그 1,000건 밖에 있으면 0건이 된다.** 0건의 원인이 "언급이 없어서"인지 "상한에 막혀서"인지 **응답만으로는 구별할 수 없다.** → `pageable_count`와 필터 통과 건수를 **둘 다 로그에 남겨야 한다** |
| **D** | 🔴 **`pageable_count` 천장** | 옛 글이 안 들어온다 | 공식 예제: `total_count` 218,662인데 `pageable_count` 983. **키워드당 1,000건 근처에서 막힌다.** "API로 옮기면 20건 천장이 사라진다"는 기대가 틀리는 지점이다 |
| **E** | 🟠 **`page > 50`에서 오류** | 요청 실패 | `is_end`만 보고 돌면 51페이지를 요청하게 된다. 루프에 `page >= 50` 조건이 필요하다 |
| **F** | 🟠 **`url`이 `http` + 데스크톱 호스트** | 중복 판정이 안 이어진다 | 공식 예제의 `url`이 `http://cafe.daum.net/...`이다. **`https`도 아니고 `m.`도 없다.** `url` 문자열을 그대로 `sourceId`로 쓰면 경로 (1)이 저장한 것과 안 맞아 **같은 글이 두 번 들어온다** |
| **G** | 🟠 **작성자가 없어진다** | `author`가 전부 빈 값 | 응답에 작성자 필드가 없다. 화면에서 작성자를 쓰고 있었다면 그 칸이 빈다 |
| **H** | 🟠 **본문이 스니펫으로 줄어든다** | 분류 정확도가 떨어진다 | `contents`는 "카페 글 내용중 일부"다. ⚠️ **길이 상한은 문서에 명시가 없다 — 실측이 필요하다** |
| **I** | 🟠 **쿼터 초과가 계약 위반이 된다** | 429 | 운영정책 제5조 31호가 "제6조에 따라 정한 제공 한도를 초과하여 서비스를 이용하는 행위"를 **금지 행동으로** 적고 있다. 단순 기술적 한도가 아니다 |
| **J** | 🔴 **가장 조용한 실패: 약관 위반은 로그에 안 남는다** | **아무 일도 안 일어난다** | `DO NOTHING`으로 영구 적재하는 동안 20호 위반 상태가 매일 누적되지만 **에러도 경고도 없다.** 알게 되는 시점은 카카오가 [운영정책 제8조](https://developers.kakao.com/terms/ko/site-policies)에 따라 **경고·데이터 삭제 요구·이용 정지**를 보낼 때다 |

## 4-9. 실측 결과 — 적법하지만 실익이 없다 (2026-09-06)

실제로 붙여서 돌려 봤다. **법적으로는 이 저장소에서 가장 깨끗한 채널인데, 이 수집기 구조로는
값이 거의 나오지 않는다.** 원인이 사슬로 물려 있다.

| 단계 | 사실 |
|---|---|
| 검색 경로 | robots.txt가 `/_search`를 막는다 → 검색을 쓸 수 없다 |
| 그래서 | 게시판 훑기만 가능 → 페이지를 넘길 수 없어 **게시판당 20건이 상한** |
| 주제가 맞는 게시판 | **달글 구조**다. 제목이 스레드 이름이라 서비스명이 제목에 안 나온다 |
| 구조가 맞는 게시판 | 주제가 안 맞거나 20건이 몇 분치다 |

한 카페(비로그인으로 보이는 게시판 4개)의 실측값이다.

| 게시판 | 형식 | 20건이 덮는 기간 | 판정 |
|---|---|---|---|
| 웹툰/소설/애니 달글 | 달글 (제목=스레드명, 내용은 댓글) | 12일 | 주제 O / 구조 X |
| 잡담 게시판 | 개별 글 | 10일 | 구조 O / 주제 X |
| 펌·유머 게시판 | 개별 글 | 35분 | 구조 O / 주제 X |
| 자유게시판 | 개별 글 | **1분** | 구조 O / 속도 X |

수집을 실행하면 정상 동작한다(`20건 훑어 0건`). 파싱도 날짜도 문제가 없다. **제목 필터에
걸리는 글이 없을 뿐이다.**

### 그래서 껐다

`sources.daum-cafe = 0`. 코드와 문서는 남긴다 — 적법성 판단은 유효하고, 카페나 게시판을
바꾸면 다시 쓸 수 있다.

### 다시 켜려면 필요한 것

| 조건 | 이유 |
|---|---|
| **개별 글이 올라오는 주제별 게시판** | 달글 게시판은 제목에 서비스명이 안 나온다 |
| **20건이 최소 며칠을 덮는 속도** | 자유게시판처럼 1분치면 걸릴 확률이 사실상 0이다 |
| (또는) **댓글 수집 확장** | 달글의 실제 반응은 댓글에 있다. 댓글 경로의 robots.txt 허용 여부를 먼저 확인해야 한다 |

### 부수 조치 — 닉네임 저장 제거

같은 날 `writerNickname`을 저장하지 않도록 고쳤다([2-4](#2-4-판정과-근거)에서 "가장 먼저 줄일 수
있는 항목"으로 지목한 것). 목록 데이터에는 여전히 닉네임이 오지만 담지 않는다. 이로써 통합서비스약관
제12조 13호("다른 이용자의 개인정보를 수집, 저장, 공개하는 행위") 적용 논쟁도 같이 사라진다.

## 5. 붙인 뒤 확인할 것

### 5-1. 경로 (1) — 실행 직후 5분 안에 확인

**① 로그 한 줄을 읽는다.** 수집기가 실행 끝에 반드시 찍는다.

```
  다음 카페: {훑은 수}건 훑어 {저장한 수}건 (본문 {N}건 확인, 반복 {M}건 제외)
```

| 값 | 정상 | 이상하면 |
|---|---|---|
| **훑은 수** | **게시판 수 × 20**에 가까워야 한다. 게시판 3곳이면 **60** | 60보다 훨씬 작으면 **비공개 게시판이 섞였다**(함정 4·5). 어느 게시판인지는 바로 위의 `글을 찾지 못했습니다` 경고에 있다 |
| **저장한 수** | 0이어도 정상일 수 있다 — 최신 20건에 우연히 언급이 없을 수 있다. **여러 번 돌려도 계속 0이면** 게시판 선택을 의심한다 | |
| **본문 N건** | 저장한 수와 같아야 한다 | **30이면 상한에 닿은 것**(함정 6). 저장한 수보다 작으면 403으로 막힌 게시판이 있다(함정 7) |

**② 저장된 글 3~5건을 눈으로 본다.** 아래를 전부 만족해야 정상이다.

| 확인 | 정상 | 아니면 |
|---|---|---|
| `sourceId`에 `/`가 **두 개** | `{카페}/{게시판}/{번호}` | 함정 12 |
| `url`을 눌러 실제 글이 열린다 | | 함정 11 |
| `content`에 **줄바꿈이 있고** 제목 뒤에 본문이 있다 | | 본문 파싱 실패 (함정 9) |
| `content`에 `북마크`, `공유하기`, `댓글 12` 같은 문구가 **없다** | | 함정 10 — 지우는 목록을 넓혀야 한다 |
| `postedAt`이 **채워져 있다** | | 함정 8 |

**③ 화면의 "작성일 없음" 필터를 본다.** 다음 카페 글이 여기 쌓이면 목록의 시각 표기가 바뀐 것이다(함정 8).

**④ 하루 뒤 커버리지를 본다.** 저장된 글의 `postedAt` 범위를 본다.

| 결과 | 판정 |
|---|---|
| 며칠~몇 주에 걸쳐 퍼져 있다 | 🟢 **주제별 게시판을 잘 골랐다.** 이 경로가 맞게 쓰이고 있다 |
| 전부 실행 직전 몇 분에 몰려 있다 | 🔴 **종합 게시판이다**(함정 3). 20건이 1~2분 분량이라 나머지를 다 놓치고 있다. 게시판을 바꾼다 |

**⑤ 상한을 잘못 이해하지 않았는지 확인한다.** 설정에서 `다음 카페` 상한을 20으로 두고 실행했을 때
게시판당 20건보다 **많이** 들어오면 무언가 잘못 읽은 것이다. 20이 물리적 상한이다.

### 5-2. 경로 (2) — 착수 전과 후

**착수 전에 반드시 통과해야 하는 것:**

- [ ] 🔴 **법무 판단**: 운영정책 제5조 **20호**(캐시 목적 제한 + 최신성 유지 의무)와 **30호**(사전 승낙 없는 복사·복제 금지)에
      `ON CONFLICT DO NOTHING` 영구 적재가 걸리는가.
      **"걸린다"면 여기서 멈춘다.** 경로 (1)이 이미 잘 돌고, 현재 수집량이 0이라 서두를 이유가 없다
- [ ] 저장 모델을 `DO UPDATE` + 주기적 재조회로 바꿀 것인지, 아니면 전환을 포기할 것인지 결정
- [ ] `source` 값을 경로 (1)과 나눌 것인지 결정
- [ ] `sourceId` 정규화 규칙 확정 (함정 F)

**붙인 뒤 확인:**

| 확인 항목 | 무엇이 나와야 정상 |
|---|---|
| `meta.pageable_count`를 로그에 남긴다 | 이 값이 실질 천장이다. 로그에 없으면 왜 적게 들어왔는지 나중에 알 수 없다 |
| **필터 통과 건수도 따로 남긴다** | `받은 건수 → cafename 필터 통과 건수 → 저장 건수` 세 숫자가 다 보여야 한다. 하나만 보면 함정 C를 못 잡는다 |
| 첫 문서의 `datetime` | **오늘~며칠 이내여야 한다.** 2년 전 날짜가 나오면 `sort=recency`가 안 걸린 것이다(함정 A) |
| 저장된 `content` | **`<b>`가 하나도 없어야 한다**(함정 B). `grep '<b>'`로 확인 |
| `is_end` 루프 | 마지막 페이지에서 멈추고, `page`가 50을 넘지 않는다(함정 E) |
| `author` | 전부 비어 있는 것이 **정상**이다(함정 G). 뭔가 채워져 있으면 잘못 매핑한 것이다 |
| `contents` 길이 분포 | ⚠️ 실측해서 이 문서에 적는다. 800자 절단이 의미 있는지 판단하는 근거다 |
