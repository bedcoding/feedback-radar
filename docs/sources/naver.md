## 2. 적법성 근거

### 2-1. robots.txt 실측 (2026-08-29)

| URL | HTTP | 내용 |
|---|---|---|
| `https://naverapihub.apigw.ntruss.com/robots.txt` | **404** | robots.txt 없음. 본문은 게이트웨이 JSON 오류 `{"error":{"errorCode":"300",...}}` |
| `https://openapi.naver.com/robots.txt` | 200 | **전면 차단** (아래 원문) |
| `https://developers.naver.com/robots.txt` | **404** | HTML 오류 페이지 |
| `https://www.ncloud.com/robots.txt` | 200 | **1바이트 빈 파일** (규칙 없음) |

**우리가 실제로 요청하는 호스트는 `naverapihub.apigw.ntruss.com` 하나뿐이고, 그 호스트에는 robots.txt가 없다.**
RFC 9309상 robots.txt가 없으면 제한이 없는 것으로 본다. 우리 경로에 걸리는 규칙은 없다.

**그런데 옛 공식 API 호스트의 robots.txt는 이렇다 (`https://openapi.naver.com/robots.txt`, HTTP 200) — 전문:**

```
User-agent: *
Disallow: /
```

**이 두 줄이 이 문서에서 가장 유용한 실측이다.** `openapi.naver.com`은 네이버가 직접 문서화하고 키를 발급하던
**공식 검색 API 호스트**인데, robots.txt는 전면 차단이다. 즉 **인증 API 앞에서 robots.txt 층위는 판정 근거가 되지
않는다.** robots.txt는 익명 크롤러용 신호이고, 키를 받아 호출하는 경로는 약관이 규율한다.

> 그래서 이 소스의 적법성은 robots.txt가 아니라 **전적으로 약관 층위에서 결정된다.**
> 아래가 이 문서의 본론이다.

### 2-2. 어느 약관이 적용되는가 — 먼저 이것부터 갈라야 한다

**같은 검색 API에 두 벌의 약관이 존재하고, 발급처에 따라 적용되는 것이 다르다.**

| 경로 | 발급처 | 적용 약관 | 우리 |
|---|---|---|---|
| `openapi.naver.com/v1/search/*` | 네이버 개발자센터 (네이버㈜) | 「NAVER API 서비스 이용약관」 (2026-07-31 개정) | ❌ 안 씀 |
| `naverapihub.apigw.ntruss.com/search/v1/*` | **NAVER Cloud → NAVER API HUB** (네이버클라우드㈜) | 「AI·Naver API 서비스 이용약관」 (2025-03-20 시행, v5) + 「네이버 클라우드 플랫폼 서비스 이용약관」 (2026-01-22, v24) | ✅ **이쪽** |

전환이 문서로 확정돼 있다. 개발자센터 약관 부칙 제2조 ④ (⚠️ **대조 미완** — 아래 상자):

### 2-3. 🔴 핵심 조항 — 카카오 20호에 해당하는 것이 네이버에도 있다

✅ **「네이버 클라우드 플랫폼 AI·Naver API 서비스 이용약관」 제5조(권리 및 의무) ⑧ — 원문:**

> ⑧ ‘고객’은 ‘회사’의 사전 동의 없이 ‘본 서비스’의 결과 데이터를 본 약관에서 허용한 범위를 넘어서서 무단으로 복제, 저장, 가공, 배포하거나 제3자에게 제공해서는 안됩니다.

같은 약관 제5조 ① — 원문:

> ① ‘고객’은 본 약관, ‘홈페이지’ 등에서 허용하는 범위 내에서 ‘본 서비스’를 사용할 수 있는 권리를 취득하는 것이며, 어떠한 경우에도 (그와 같은 제한된 사용권의 부여를 넘어선) ‘본 서비스’와 관련된 지식재산권 혹은 관련 권리의 취득 혹은 결과 데이터에 대한 권리의 취득을 의미하지는 않습니다.

- 출처: <https://www.ncloud.com/policy/terms/opapi> (원문 PDF 링크가 이 페이지에서 제공된다. 2025-03-20 시행, v5)

**이 도구가 무엇을 하고 있는지와 대조하면:**

| 조항의 금지 행위 | 이 도구 |
|---|---|
| 무단 **저장** | `items` 표에 **영구 적재.** 보유기간 정책도 삭제 코드도 없다 (`ON CONFLICT ... DO NOTHING`, [store.ts](../../packages/core/src/store.ts)) |
| 무단 **가공** | 제목·스니펫을 합치고 `<b>` 태그를 걷어낸 뒤 **LLM에 넣어 감성·카테고리·심각도를 붙인다** |
| 무단 **제3자 제공** | 분류를 위해 본문이 **LLM 제공자에게 전달된다** |
| **배포** | 하지 않는다. 외부 공개가 없다 |

**"허용한 범위"가 무엇인지 약관 문언만으로는 정해지지 않는다.** 같은 약관 제3조 ③이
사용범위·이용 횟수 등의 제공 조건을 "‘홈페이지’를 통해 공지"한다고 넘기고 있어서, 허용 범위의 실체는
네이버클라우드가 홈페이지에 게재한 서비스별 안내에 있다. **그 안내에서 검색 API의 저장 허용 범위를
정한 문서는 이번 조사에서 찾지 못했다.** 그리고 사전 동의를 받은 사실도 없다.

### 2-4. 카카오와 무엇이 같고 무엇이 다른가

| | 카카오 운영정책 제5조 20호 | 네이버클라우드 AI·Naver API 약관 제5조 ⑧ |
|---|---|---|
| 저장·캐시 제한 | 있다 | **있다** |
| **최신성 유지 의무** | 있다 ("캐시 후 최신 데이터로 유지하지 않는 행위") | **없다** |
| 걸리는 방식 | 영구 적재 + 미갱신이 **조항 후단에 정면으로** 걸린다 | "사전 동의 없는 무단 저장·가공"이라는 **일반 금지**에 걸리는지가 "허용한 범위" 해석에 달린다 |

**네이버 쪽이 카카오보다 약하게 걸린다.** 카카오는 "갱신하지 않으면 위반"이라고 행위를 특정했지만,
네이버는 허용 범위를 약관 밖(홈페이지 공지)으로 넘겼다. 그래서 **카카오처럼 "정면으로 걸린다"고
단정할 수 없고, 동시에 "문제없다"고도 할 수 없다.** 이것이 🟡의 이유다.

### 3-3. 우리가 실제로 얼마나 쓰나

**세는 단위가 "건"이 아니라 "호출(요청) 횟수"다.** `display=100`으로 100건을 받아도 **1회**다.
`display`를 올리는 것은 쿼터를 더 쓰지 않는다. 쿼터를 쓰는 것은 **키워드 수 × 채널 수 × 페이지 수**다.

```
하루 호출 수 = 키워드 수 × 채널 2(블로그·카페) × 페이지 수 × 하루 실행 횟수
```

| 시나리오 | 계산 | 하루 호출 | 일 한도 25,000 대비 |
|---|---|---:|---:|
| **현재 코드** (페이지네이션 없음, 하루 1회) | 9 × 2 × 1 × 1 | **18회** | **0.07%** |
| `start` 루프 10쪽 도입 ([4-5](#4-5-상한쿼터페이지네이션)) | 9 × 2 × 10 × 1 | **180회** | 0.72% |
| 위 + 1시간 주기 | 9 × 2 × 10 × 24 | **4,320회** | 17.3% |
| 한도에 닿는 지점 | — | 25,000회 | **키워드 9개·10쪽이면 하루 138회차** |

- 키워드 수 9개는 설정 실측값이다([`../api-costs.md`](../api-costs.md) 3절, 감시 서비스 전체 합계 서비스별로 나뉜다).
  **키워드가 늘면 호출도 비례해 는다.**
- **결론: 어떤 시나리오에서도 돈이 들지 않고, 쿼터도 여유가 있다.** 이 소스에서 비용은 의사결정 변수가 아니다.
- ⚠️ 단, **수집한 뒤 LLM 분류에는 돈이 든다.** 그리고 [4-6](#4-6-함정) 12번대로 이 채널은
  관련 없는 글 비율이 33~43%라 **분류 비용의 그만큼이 버려진다.** 이 소스에서 실제로 돈이 새는 곳은 API가 아니라 여기다.

## 4. 연동 방법

### 4-1. 사전 준비 (사람이 해야 하는 것)

**2026년부터 발급처가 바뀌었다. 개발자센터에서는 신규 발급이 불가능하다.**

| # | 할 일 | 누가 | 확인된 근거 |
|---|---|---|---|
| 1 | **NAVER Cloud Platform 계정** 준비 | 계정·결제 권한을 가진 사람. 개발자 혼자 못 끝낼 수 있다 | 발급처가 네이버클라우드㈜다 |
| 2 | 콘솔에서 **NAVER API HUB → 검색 API** 이용 신청 | 위와 같음 | ⚠️ **확인 필요** — 콘솔 화면 절차를 이 조사에서 직접 밟지 않았다. 확인한 것은 "발급 결과물이 키 한 쌍이고 그 값으로 즉시 호출이 된다"까지다 |
| 3 | 발급된 **API Key ID / API Key** 두 값을 `.env`에 넣는다 | 개발자 | 실측: 이 두 값만으로 HTTP 200 |

**환경변수는 셋이다 — 둘은 필수, 하나는 선택이다.**

| 변수 | 필수 | 값 | 기본값 |
|---|---|---|---|
| `NAVER_CLIENT_ID` | **Y** | NCP **API Key ID** | 없음. 없으면 수집기가 스킵 로그를 찍고 빈 배열 |
| `NAVER_CLIENT_SECRET` | **Y** | NCP **API Key** | 없음. **없어도 로그가 안 나온다** → [4-6](#4-6-함정) 2번 |
| `NAVER_API_BASE` | N | 베이스 주소 교체용 (스테이징·목 서버) | `https://naverapihub.apigw.ntruss.com/search/v1` — **보통 건드리지 않는다** |

```
NAVER_CLIENT_ID=<API Key ID>
NAVER_CLIENT_SECRET=<API Key>
# NAVER_API_BASE는 보통 설정하지 않는다. 기본값이 아래와 같고, 채널 세그먼트가 붙지 않는다.
# NAVER_API_BASE=https://naverapihub.apigw.ntruss.com/search/v1
```

> 🔴 **`NAVER_API_BASE`에 `/blog`나 `/cafearticle`까지 넣으면 안 된다.** 코드가
> `${NAVER_API_BASE}/${endpoint}`로 조립하므로 경로가 겹쳐 `/search/v1/blog/blog` → **404**가 된다.
> 그리고 [4-6](#4-6-함정) 1번 때문에 그 404가 화면에는 **"성공, 0건"**으로 보인다. → [4-3](#4-3-엔드포인트와-요청)

> **변수 이름이 개발자센터 시절 그대로다.** 값은 NCP 키인데 이름은 `NAVER_CLIENT_*`라
> 헷갈린다. 이름만 보고 개발자센터 키를 넣으면 401이 난다.

**함정 세 가지 — 전부 코드 주석에 이력이 남아 있다.**

1. ❌ **개발자센터에서 신규 발급은 안 된다.** '사용 API' 목록에 '검색' 항목 자체가 없어졌다.
   약관 부칙 제2조 ①이 2026-07-30 24:00부로 신규 접수 중단을 명시한다
2. ❌ **개발자센터 드롭다운의 '카페'를 골라 받은 키로는 안 된다.** 그건 카페 **가입·글쓰기용**
   로그인 오픈 API이고 access token을 요구한다. 공개 카페 글 **검색**과는 다른 API다
3. ❌ **쇼핑·책·전문자료 검색은 2026-07-31 24:00부로 완전히 종료됐다.** 대체 API가 없다.
   블로그·뉴스·카페글 같은 일반 검색만 HUB로 이관돼 살아 있다 (부칙 제2조 ③.
   ⚠️ **대조 미완** — [2-2](#2-2-어느-약관이-적용되는가--먼저-이것부터-갈라야-한다)의 상자.
   보강 근거: HUB 공식 문서에 `/search/v1/shop`·`/search/v1/book` 페이지가 없다. 다만 **문서 부재는 종료의 증명이 아니다**)
   - 📌 **명칭 주의: 세 번째는 「전문자료」다. "학술정보"라는 이름의 검색 API는 없다.**
     코드 주석([`naver.ts:53`](../../apps/pipeline/src/collectors/naver.ts))과
     [적법성 문서](../data-collection-compliance.md)도 「전문자료」로 적는다.
     위 **대조 미완**을 닫을 때([5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 1번)
     틀린 이름으로 원문을 뒤지면 조항 자체를 못 찾는다.

> **기존 개발자센터 키를 아직 쓰고 있다면 만료일이 있다.** 부칙 제2조 ②에 따라
> **2027년 6월 30일 24:00**까지만 개발자센터 경로가 제공된다. 그 전에 HUB로 옮겨야 한다.
> ⚠️ 이 날짜도 위 **대조 미완** 인용에 걸려 있다. 확인 절차 → [5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 1번.
> **새로 붙이는 사람에게는 실무 영향이 없다** — 어차피 개발자센터 신규 발급이 막혀 HUB 키를 받게 된다.

### 4-2. 인증

**정적 키 두 개를 헤더에 넣는 것이 전부다. 토큰도, 서명도, 갱신도 없다.**

```
X-NCP-APIGW-API-KEY-ID: {API Key ID}
X-NCP-APIGW-API-KEY: {API Key}
```

| 항목 | 값 |
|---|---|
| 방식 | 헤더 두 개. Bearer 토큰도 JWT도 OAuth도 아니다 |
| 토큰 수명 | **없다.** 만료되지 않는 정적 키 |
| 갱신 절차 | **없다.** Threads(60일 회전)·구글플레이(1시간 토큰)와 달리 회전 자격증명 설계가 필요 없다 |
| 계정별로 키가 갈리나 | 아니다. **한 벌이면 된다.** 앱스토어(판매자 계정마다 .p8 2벌)와 다른 점이다 |

**❌ 옛 헤더는 이 호스트에서 통하지 않는다.** 실측:

| 보낸 것 | 결과 |
|---|---|
| `X-NCP-APIGW-API-KEY-ID` + `X-NCP-APIGW-API-KEY` (올바른 값) | **HTTP 200** |
| `X-Naver-Client-Id` + `X-Naver-Client-Secret` (개발자센터 시절 헤더) | **HTTP 401** |
| 헤더 없음 | HTTP 401 |
| 헤더는 맞는데 키 값이 틀림 | HTTP 401 |

**401 응답 본문은 위 세 경우가 전부 똑같다** (실측):

```json
{"error":{"errorCode":"200","message":"Authentication Failed","details":"Authentication information are missing."}}
```

> ⚠️ **`details`가 "missing"이라고 말해도 값이 틀린 경우일 수 있다.** 이 메시지를 곧이곧대로 읽고
> "환경변수가 안 들어갔나" 쪽만 파면 시간을 버린다. 헤더 이름과 값을 둘 다 의심해야 한다.

### 4-3. 엔드포인트와 요청

| 채널 | 엔드포인트 | `items.source` |
|---|---|---|
| 블로그 | `GET https://naverapihub.apigw.ntruss.com/search/v1/blog` | `naver-blog` |
| 카페글 | `GET https://naverapihub.apigw.ntruss.com/search/v1/cafearticle` | `naver-cafe` |
| (참고) 뉴스 | `GET .../search/v1/news` | 수집 안 함. **같은 키로 200이 뜬다**(실측). 채널을 늘릴 여지가 있다 |

- 프로토콜 HTTPS, 메서드 GET
- ❌ **경로 끝에 `.json`을 붙이면 404다.** 개발자센터 시절 주소(`/v1/search/blog.json`)의 습관이다.
  실측: `.../search/v1/blog.json` → `HTTP 404 {"error":{"errorCode":"300","message":"Not Found Exception"}}`

**베이스 주소와 채널 세그먼트는 분리돼 있다. 위 표의 풀 URL을 그대로 환경변수에 넣으면 404다.**

| | 값 |
|---|---|
| `NAVER_API_BASE` **기본값** | `https://naverapihub.apigw.ntruss.com/search/v1` — **채널 세그먼트 없음** |
| 최종 URL 조립 | `${NAVER_API_BASE}/blog` 또는 `${NAVER_API_BASE}/cafearticle` |
| 코드 | [`naver.ts:56`](../../apps/pipeline/src/collectors/naver.ts) `const HUB_BASE = process.env.NAVER_API_BASE ?? 'https://naverapihub.apigw.ntruss.com/search/v1'`, 조립은 [`naver.ts:62`](../../apps/pipeline/src/collectors/naver.ts)의 `` `${HUB_BASE}/${endpoint}?...` `` |

> 🔴 **위 표의 풀 URL(`.../search/v1/blog`)을 `NAVER_API_BASE`에 넣으면 `/search/v1/blog/blog`가 되어 404다.**
> `.json`을 붙였을 때와 **똑같은 게이트웨이 404**(`errorCode 300`)이고, [4-6](#4-6-함정) 1번 때문에
> 화면에는 **"성공, 0건"**으로만 보인다. → [4-6](#4-6-함정) 6번

**파라미터 — 다섯 개가 전부다.** (HUB 공식 문서 원문 + 실측으로 교차 확인.
출처: <https://api.ncloud-docs.com/docs/ko/naver-api-hub-search-blog>, 카페글도 동일)

| 파라미터 | 타입 | 필수 | 설명 (공식 문서 표기) | 실측 |
|---|---|---|---|---|
| `query` | String | **Y** | 검색어 - UTF-8로 인코딩 | 빠지면 `HTTP 400 / SE01` |
| `display` | Integer | N | 한 번에 표시할 검색 결과 개수 - `1`~`100` (기본값: `10`) | 100 → 200 OK / 101 → `400 SE02` |
| `start` | Integer | N | 검색 시작 위치 - `1`~`1000` (기본값: `1`) | 1000 → 200 OK / 1001 → `400 SE03` |
| `sort` | String | N | 검색 결과 정렬 방법 - `sim` (기본값) \| `date` | 아래 경고 참고 |
| `format` | String | N | 응답 형식 - `json` (기본값) \| `xml` | 이 조사에서 보내 보지 않았다. 현재 코드도 **보내지 않는다**(기본값이 json이라 불필요) |

> 🔴 **`sort`를 빼면 `sim`이다.** 실측에서 `sort=sim`은 2019년 글을 첫 결과로 돌려줬다.
> 최신 반응 모니터링이 목적이면 **반드시 `sort=date`를 명시**한다. 현재 코드는 명시하고 있다.

> ⚠️ **`format`으로 [4-6](#4-6-함정) 4번(성공 응답이 `text/plain`)이 해결되는지는 확인 필요.**
> 이 파라미터는 공식 문서상 **본문 형식**(json/xml)을 고르는 것이고, `format=json`이 응답
> `Content-Type`을 `application/json`으로 바꿔 주는지는 **문서에 적혀 있지 않고 이 조사에서 보내 보지도 않았다.**
> 기본값이 이미 json이라 현재 코드는 안 보낸다. 판별 절차 → [5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 3번.

**검색 오류(400) 응답 본문 — 게이트웨이 오류와 모양이 다르다**

401은 [4-2](#4-2-인증)에, 404는 이 절 앞쪽의 `.json` 항목에 **실측 본문**을 그대로 실어 두었다.
검색 오류(400) 계열은 필드 이름부터 다르다(→ [4-6](#4-6-함정) 5번). 파싱해야 하는 모양은 이렇다:

```json
{"errorMessage":"Invalid display value","errorCode":"SE02"}
```

> ⚠️ **이 한 줄만 실측 리터럴이 아니다.** 필드 이름 두 개(`errorMessage`, `errorCode`)는 [4-6](#4-6-함정) 5번이 확정한 것이고,
> **값**은 HUB 공식 문서 오류표(아래)의 코드·메시지를 그 필드에 넣어 **재구성**한 것이다.
> 401·404와 달리 이 계열은 본문 문자열이 기록되지 않았다. 실측 본문을 뜨는 절차 → [5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 11번.
> **그러므로 `errorMessage` 문자열로 분기하면 안 된다.** 갈라야 하는 것은 `errorCode`다.

HUB 공식 문서의 오류 코드 표 원문 (<https://api.ncloud-docs.com/docs/ko/naver-api-hub-search-blog>, 2026-08-30 재확인):

| HTTP | `errorCode` | `errorMessage` (공식 문서 표기) | 공식 문서의 조치 설명 |
|---|---|---|---|
| 400 | `SE01` | Incorrect query request | API 요청 URL의 프로토콜, 파라미터 등 확인 |
| 400 | `SE02` | Invalid display value | display 값 허용 범위 확인 |
| 400 | `SE03` | Invalid start value | start 값 허용 범위 확인 |
| 400 | `SE04` | Invalid sort value | sort 값 오타 확인 |
| 400 | `SE06` | Malformed encoding | 검색어를 UTF-8로 인코딩 |
| 404 | `SE05` | Invalid search api | API 요청 URL 오타 확인 |
| 500 | `SE99` | System Error | 서버 내부 오류 발생 |

**공식 문서에 403 행이 없다**는 것도 이 표에서 나온 사실이다(→ [5-1](#5-1-키가-살아-있는지-10초-db를-건드리지-않는다) 403 행,
[5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 5번). 그리고 **오류 본문 예시(JSON)는 공식 문서에 없다** — 성공 응답만 실려 있다.

**요청 예 (그대로 실행 가능)**

```bash
curl -s \
  -H "X-NCP-APIGW-API-KEY-ID: $NAVER_CLIENT_ID" \
  -H "X-NCP-APIGW-API-KEY: $NAVER_CLIENT_SECRET" \
  --max-time 15 \
  "https://naverapihub.apigw.ntruss.com/search/v1/blog?query=%EC%9B%B9%ED%88%B0&display=3&sort=date"
```

**코드로 옮기면 이렇다. 타임아웃은 선택이 아니다** ([4-6](#4-6-함정) 15번):

```ts
// 모듈 최상단. 채널 세그먼트가 붙지 않은 베이스만 담는다 (→ 위 🔴 상자)
const HUB_BASE = process.env.NAVER_API_BASE ?? 'https://naverapihub.apigw.ntruss.com/search/v1';

// ── 자격증명은 여기서 끝이다. 토큰 교환도 서명도 갱신도 없다 (→ 4-2)
const id = process.env.NAVER_CLIENT_ID;      // = NCP API Key ID
const secret = process.env.NAVER_CLIENT_SECRET; // = NCP API Key
if (!id || !secret) return [];
// ⚠️ 현행 코드의 이 분기는 로그를 한 줄도 안 남긴다. 시크릿만 비면 조용히 0건이 된다 → 4-6 2번.
// 새로 짠다면 여기에 console.warn을 넣는다 (→ 5-3 2번)

const url = `${HUB_BASE}/${endpoint}?query=${encodeURIComponent(query)}&display=${display}&sort=date`;
let res: Response;
try {
  res = await fetch(url, {
    headers: { 'X-NCP-APIGW-API-KEY-ID': id, 'X-NCP-APIGW-API-KEY': secret },
    signal: AbortSignal.timeout(15_000), // 없으면 키워드마다 매달린다
  });
} catch (e) {
  // AbortSignal.timeout은 throw한다. res.ok 분기로는 절대 안 잡힌다
  console.warn(`네이버 API 요청 실패 (${endpoint}): ${(e as Error).message}`);
  return [];
}
```

현행 구현: 베이스 [`naver.ts:56`](../../apps/pipeline/src/collectors/naver.ts) ·
자격증명 두 줄과 빈 값 분기 [`naver.ts:59-61`](../../apps/pipeline/src/collectors/naver.ts) ·
URL 조립과 요청 [`naver.ts:62-73`](../../apps/pipeline/src/collectors/naver.ts).
**환경변수 이름은 [4-1](#4-1-사전-준비-사람이-해야-하는-것)의 표와 같은 것이고, 코드가 읽는 자리는 이 두 줄뿐이다.**
`encodeURIComponent`가 `query`의 UTF-8 퍼센트 인코딩을 담당한다. 공식 문서가 `query`를
"UTF-8로 인코딩"으로 규정하고, 인코딩이 잘못되면 `400 / SE06 Malformed encoding`이 온다([5-1](#5-1-키가-살아-있는지-10초-db를-건드리지-않는다)).

**응답 예 — 실측 응답에서 값만 자리표시자로 바꾼 것** (구조는 실제 그대로다)

```json
{
  "lastBuildDate": "Sat, 29 Aug 2026 23:03:37 +0900",
  "total": 854500,
  "start": 1,
  "display": 3,
  "items": [
    {
      "title": "제목에 검색어가 <b>강조</b>돼서 온다",
      "link": "https://blog.naver.com/{블로그ID}/{글번호}",
      "description": "본문을 요약한 패시지. <b>검색어</b>가 강조되고 대개 ... 로 끝난다 ",
      "bloggername": "블로그 이름",
      "bloggerlink": "https://blog.naver.com/{블로그ID}",
      "postdate": "20260829"
    }
  ]
}
```

카페글은 `items[]`의 구성이 다르다 (실측):

```json
{
  "title": "게시글 제목",
  "link": "https://cafe.naver.com/{카페ID}/{글번호}",
  "description": "요약 패시지",
  "cafename": "카페 이름",
  "cafeurl": "https://cafe.naver.com/{카페ID}"
}
```

> 🔴 **성공 응답의 `Content-Type`이 `text/plain;charset=UTF-8`이다** (실측). `application/json`이 아니다.
> 오류 응답만 `application/json`으로 온다. content-type을 보고 파싱 여부를 가르는 클라이언트는
> **성공을 조용히 버린다.** → [4-6](#4-6-함정) 4번

### 4-4. 응답 → RawItem 매핑

`RawItem`은 [`packages/core/src/types.ts`](../../packages/core/src/types.ts)에 있다.

| RawItem 필드 | 블로그 (`blog`) | 카페 (`cafearticle`) | 비고 |
|---|---|---|---|
| `source` | 고정 `'naver-blog'` | 고정 `'naver-cafe'` | 채널이 갈려 있어 켜고 끄기·필터가 따로 논다 |
| `sourceId` | `link` | `link` | **URL을 그대로 식별자로 쓴다.** 중복 판정 키가 `(source, source_id)`다 |
| `url` | `link` | `link` | `sourceId`와 같은 값 |
| `author` | `bloggername` (**블로그 이름**) | `cafename` (**카페 이름**) | ⚠️ 둘 다 "글쓴이"가 아니다. 카페는 작성자 정보가 응답에 **아예 없다** |
| `content` | `strip(title) + "\n" + strip(description)` | 같음 | ⚠️ **본문이 아니라 검색 스니펫이다.** 아래 참고 |
| `rating` | ❌ **못 채운다** | ❌ **못 채운다** | 별점 개념이 없다 |
| `postedAt` | `postdate`(`YYYYMMDD`) → **로컬 오프셋 ISO**. 시각은 00:00 고정. 문자열 형식은 아래에 못박았다 | ❌ **못 채운다.** 응답에 필드가 없다 | 이 차이가 두 채널을 가르는 가장 큰 항목이다 |
| `keyword` | 호출에 쓴 검색어 | 같음 | |
| `service` | 호출부에서 주입 | 같음 | 여러 자사 서비스를 함께 추적할 때 구분용 |
| `country` | ❌ 비워 둔다 | ❌ 비워 둔다 | 앱 리뷰 전용 개념이다 |

**🔴 `postedAt` 문자열 형식 — 여기서 틀리면 조용히 하루가 밀린다**

이 저장소는 `posted_at`을 **문자열 사전순으로** 비교해 기간 필터와 정렬을 건다
([`time.ts:1-8`](../../packages/core/src/time.ts)의 파일 머리 주석). 그래서 형식이 규격이다.

| | 값 |
|---|---|
| **입력** | `postdate` = `"20260829"` |
| **저장해야 하는 값** | `"2026-08-29T00:00:00.000+09:00"` |
| 형식 | `YYYY-MM-DDTHH:mm:ss.SSS±HH:MM` — **밀리초 3자리 + 명시적 로컬 오프셋** |
| 만드는 함수 | [`time.ts:84-91`](../../packages/core/src/time.ts)의 `fromDottedDateTime()` → 내부에서 [`time.ts:20-26`](../../packages/core/src/time.ts)의 `localIso()` |
| 현행 호출 | [`naver.ts:120-124`](../../apps/pipeline/src/collectors/naver.ts) — `YYYYMMDD`를 `slice`로 잘라 `"2026.08.29"` 점 표기로 만든 뒤 `fromDottedDateTime()`에 넘긴다 |

그대로 쓸 수 있는 코드:

```ts
import { fromDottedDateTime } from '@feedback-radar/core';

// r.postdate === '20260829'
const postedAt = r.postdate
  ? fromDottedDateTime(`${r.postdate.slice(0, 4)}.${r.postdate.slice(4, 6)}.${r.postdate.slice(6, 8)}`)
  : undefined; // 카페는 항상 이쪽. '작성일 미확인'이 틀린 날짜보다 낫다
// postedAt === '2026-08-29T00:00:00.000+09:00'  (KST에서 실행할 때)
```

> ❌ **`new Date(...).toISOString()`을 쓰면 안 된다.** 처음 구현하는 사람이 가장 자연스럽게 집는 함수인데
> KST에서 `2026-08-29`가 **`"2026-08-28T15:00:00.000Z"`**가 된다. 두 가지가 동시에 깨진다:
> **(1) 날짜가 하루 밀린다** — 8/29 글이 8/28로 잡혀 그날 브리핑에서 빠진다.
> **(2) 다른 소스와 사전순 비교가 깨진다** — `"...T15:00:00.000Z"`와 `"...T00:00:00.000+09:00"`은
> 같은 시각이어도 문자열이 달라, 목록 정렬과 기간 필터가 어긋난다(`time.ts` 머리 주석이 명시한 함정이다).
> **오류가 안 나고 값도 그럴듯해서 아무도 눈치채지 못한다.** → [4-6](#4-6-함정) 16번,
> 검증은 [5-2](#5-2-수집이-실제로-들어왔는지)의 오프셋 확인 행.

**`content`에 대해 반드시 알아야 할 것**

- `description`은 **본문 전문이 아니라 검색 결과 스니펫**이다. 공식 문서 표현으로 "내용을 요약한 패시지 정보"다
- 실측 길이: **블로그 43~180자, 카페 0~183자** (각 200건 표본)
- 실측 200건 중 **블로그 190건, 카페 131건이 `...`로 끝난다** — 잘려서 온다는 뜻이다
- **카페는 `description`이 빈 문자열인 경우가 있다** (실측 최소 0자). 그러면 `content`가 제목만 남는다
- `<b>`, `</b>` 태그가 검색어에 붙어서 온다. 실측에서 나온 태그는 이 둘뿐이다
- HTML 엔티티는 실측에서 `&quot;` `&lt;` `&gt;` `&amp;` 네 종류가 나왔고, **수집기의 변환표가 이 넷을 모두 덮는다**
  ([`naver.ts:12-20`](../../apps/pipeline/src/collectors/naver.ts)의 `ENTITIES` — 표에는 `apos`, `nbsp`, `#39`도 있어 총 7개).
  **변환표에 없는 엔티티가 오면 원문 그대로 저장된다** — [`naver.ts:36`](../../apps/pipeline/src/collectors/naver.ts)의
  `strip()`이 모르는 이름은 `?? m`으로 되돌려 놓기 때문이다. 조용한 오염이고, 이걸 잡는 검사는
  **아는 엔티티가 아니라 `&...;` 패턴 전체**를 봐야 한다 → [4-6](#4-6-함정) 17번, [5-2](#5-2-수집이-실제로-들어왔는지)

**끝내 못 채우는 것 (이 API가 주지 않는다)**

조회수, 댓글 수, 좋아요, 작성자 개인 식별자, 본문 전문, 카페 게시판 이름, **카페 작성일**.

> 📌 **카페 작성일 없음이 화면까지 파급된다.** 작성일이 없으면 기간 필터와 날짜별 브리핑에서
> 통째로 빠진다. 그래서 `ItemQuery`에 `undated` 플래그가 따로 있다
> (`postedFrom`과 같이 주면 결과가 0건이 된다). 카페 345건이 전부 여기에 해당한다.

### 4-5. 상한·쿼터·페이지네이션

| 항목 | 값 | 근거 |
|---|---|---|
| `display` 범위 | **1 ~ 100** (기본 10) | ✅ HUB 공식 문서 + 실측(101 → `400 SE02`) |
| `start` 범위 | **1 ~ 1000** (기본 1) | ✅ HUB 공식 문서 + 실측(1001 → `400 SE03`) |
| **한 질의로 받을 수 있는 최대** | **1,000건** (`start` 상한 때문) | 위 두 값의 곱이 아니라 `start` 상한이 천장이다 |
| **일 호출 한도** | **25,000회** — 검색 카테고리 **통합**(블로그·카페글·뉴스가 같은 지갑) | ✅ **HUB 공식 문서 원문**(아래 인용) |
| 월 호출 한도 | **775,000회** = 25,000 × 31의 산술 누적. **버스트로 몰아 쓸 수 없다** | ✅ 요금표 FAQ → [3절](#3-비용) |
| 쿼터 잔량 헤더 | **없다** | 실측 응답 헤더는 `x-ncp-apigw-response-origin`, `x-ncp-trace-id`뿐이다. 남은 호출 수를 응답으로 알 방법이 없다 |
| 429 동작 | ⚠️ **확인 필요** | 한도를 일부러 소진해 보지 않았다. 잠정 정책은 이 절 아래 **호출 정책** 표, 판별은 [5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 2번 |

일 한도의 근거 — <https://api.ncloud-docs.com/docs/ko/naver-api-hub-search-blog> 원문:

> 블로그 검색은 검색 API를 사용하며, 검색 API의 하루 호출 한도는 25,000회입니다.

카페글 문서에도 같은 문장이 있다(<https://api.ncloud-docs.com/docs/ko/naver-api-hub-search-cafearticle>).
**이전 판이 "개발자센터 문서 기준이라 HUB에서도 같은지 모른다"고 달아 둔 ⚠️는 잘못된 것이었다** —
HUB 공식 문서에 같은 숫자가 그대로 있다. [6절](#6-출처) 정정 참고.

**`total`을 믿으면 안 된다.** 실측에서 `total`은 854,500(블로그) / 573,831(카페)로 나왔지만
`start`가 1000에서 막히므로 **실제로 받을 수 있는 것은 1,000건까지**다. `total`은 "네이버 검색에 이만큼 있다"는
숫자이지 페이지를 넘길 수 있는 범위가 아니다.

**페이지 넘기는 법**

```
1쪽: start=1     &display=100
2쪽: start=101   &display=100
3쪽: start=201   &display=100
...
10쪽: start=901  &display=100   ← 여기까지. start=1001은 400
```

실측: 1쪽 100건과 2쪽 100건의 `link` 중복 **0건**. 페이지네이션이 깔끔하게 갈린다.
같은 질의를 연속 두 번 던졌을 때 상위 20건이 완전히 일치했다 — 결과가 요청마다 흔들리지 않는다.

**🔴 현재 코드에는 페이지네이션이 없다.**

```
현재: 키워드당 1회 호출, start 미사용 → 최대 display(=최대 100)건
가능: start를 돌리면 키워드당 최대 1,000건
```

수집기의 설정 상한(`naverBlogDisplay` / `naverCafeDisplay`)은 **최소 10, 최대 100, 기본 50**이고,
배포판 기본값은 10이다([`collect-limits.ts:109-110`](../../packages/core/src/collect-limits.ts) —
`min: 10, max: 100, def: 50, perUnit: 1, scope: 'keyword'`, 배포판 기본값은 같은 파일 **146-147행**).
이 값이 그대로 `display` 파라미터가 된다([`daily.ts:302,308`](../../apps/pipeline/src/daily.ts)의
`limits.naverBlogDisplay` → `collectNaver(channel, svc.keywords, display, svc.name)`).
즉 **화면에서 상한을 최대(100)로 올려도 키워드당 100건이 천장**이고, 그 위 900건은 코드가 안 가져온다.
수집량을 늘려야 한다면 상한을 올리는 게 아니라 **`start` 루프를 넣는 것이 답이다.**

> ⚠️ **다만 상한을 올려도 안 늘어나는 구간이 있다.** 실측에서 넓은 키워드로 `display=100` × 2쪽(200건)을
> 받았더니 **200건이 전부 같은 날짜**였다. 검색량이 많은 키워드는 100건으로 하루도 못 덮는다.
> 반대로 자사 서비스처럼 좁은 키워드는 50건이면 몇 년치가 다 들어온다(실측 블로그 최고 오래된 글 수년 전).
> **키워드의 폭에 따라 같은 숫자가 전혀 다른 의미가 된다.**

**호출 정책 — 간격·동시성·재시도**

문서에 정책이 없으면 구현자가 각자 다르게 짠다. 아래를 기본값으로 쓴다.

| 항목 | 값 | 근거 / 이유 |
|---|---|---|
| **키워드 사이 지연** | **0ms (현재)** → `start` 루프 도입 시 **200ms** | 현행 코드에 지연이 **없다**([`naver.ts:107-108`](../../apps/pipeline/src/collectors/naver.ts)의 `for (const kw of keywords)`가 곧바로 `await search(...)`). 키 하나당 **50 RPS** 제한이 별도로 있으므로([3절](#3-비용)) 순차 호출 18회는 문제가 없지만, 페이지 루프로 호출이 10배가 되면 여유를 둔다 |
| **동시성** | **1 (순차)** | 현행 그대로 유지한다. `Promise.all`로 키워드를 병렬화하면 50 RPS와 25,000회 한도를 동시에 압박하는데, 얻는 것은 수십 초뿐이다 |
| **요청 타임아웃** | **15초** (`AbortSignal.timeout(15_000)`) | [`naver.ts:68`](../../apps/pipeline/src/collectors/naver.ts). **필수다** → [4-6](#4-6-함정) 15번 |
| **5xx / `SE99` 재시도** | **최대 2회**, 간격 **1초 → 4초** (지수 백오프) | 5-1 표의 "재시도"를 숫자로 확정한 값. 3회를 넘기지 않는 것은 일 배치라 다음 회차가 어차피 오기 때문이다 |
| **4xx 재시도** | **하지 않는다** | `SE01`~`SE06`·401·404는 재시도해도 같은 결과다. 파라미터·키·경로 문제다 |
| **429 처리** | ⚠️ **동작 미확인이므로 잠정 정책**: **재시도하지 않고 그 소스의 수집을 즉시 중단**하고, 사유를 `collect_progress.note`에 남긴다(`state: 'failed'`) | 한도를 소진해 보지 않아 헤더·본문·복구 시점을 모른다. **모르는 상태에서 재시도하면 한도를 더 태운다.** 실제 동작이 확인되면 이 행을 고친다 → [5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 2번 |

**`start` 루프를 넣으면 호출이 몇 배가 되나**

```
하루 호출 수 = 키워드 수 × 채널 2 × 페이지 수 × 하루 실행 횟수
```

| | 페이지 1 (현재) | 페이지 10 |
|---|---:|---:|
| 키워드 9개, 하루 1회 | 18회 | **180회** |
| 키워드 9개, 하루 24회 | 432회 | **4,320회** |

**어느 쪽도 일 25,000회에 닿지 않는다.** 즉 `start` 루프를 막는 것은 쿼터가 아니라
**LLM 분류 비용**이다([4-6](#4-6-함정) 12번 — 걸려 오는 글의 33~43%가 무관하다).

### 4-6. 함정

**조용히 실패하는 지점부터.**

| # | 함정 | 무슨 일이 벌어지나 |
|---|---|---|
| **1** | 🔴 **HTTP 오류가 전부 0건으로 둔갑한다** | 수집기는 `res.ok`가 아니면 `console.warn` 한 줄을 찍고 **빈 배열을 반환**한다([`naver.ts:74-79`](../../apps/pipeline/src/collectors/naver.ts)). 파이프라인은 그 결과를 `state: 'done', collected: 0, inserted: 0`으로 기록하고 **`note`를 남기지 않는다**([`daily.ts:460`](../../apps/pipeline/src/daily.ts) — `markCollectTask(runId, i, { state: 'done', collected: items.length, inserted })`에 `note`가 없다). 즉 **키가 만료돼도 화면에는 "성공, 0건"으로 뜬다.** 언급이 없어서 0건인 것과 구별할 방법이 없다 |
| **2** | 🔴 **`NAVER_CLIENT_SECRET`만 비면 경고조차 없다** | `collectNaver()`는 `NAVER_CLIENT_ID`만 검사해서 스킵 메시지를 찍는다([`naver.ts:102-105`](../../apps/pipeline/src/collectors/naver.ts)). 시크릿이 빈 값이면 그 검사를 통과하고, 실제 요청 함수의 `if (!id || !secret) return []` 분기는([`naver.ts:59-61`](../../apps/pipeline/src/collectors/naver.ts)) **로그를 남기지 않는다.** 키워드마다 조용히 0건이 되고 콘솔에 한 글자도 안 나온다 |
| **3** | 401 본문이 원인을 잘못 가리킨다 | 헤더 누락·키 오류·옛 헤더 사용이 **전부 같은 401 + "Authentication information are missing"** 이다. "값이 없다"고 읽으면 안 된다 |
| **4** | 성공 응답이 `text/plain`이다 | `Content-Type: text/plain;charset=UTF-8`. content-type으로 JSON 파싱 여부를 가르는 클라이언트(예: 일부 HTTP 라이브러리의 자동 파싱)는 **본문을 문자열로 넘겨준다.** Node의 `res.json()`은 무시하고 파싱하므로 현재 코드는 무사하다 |
| **5** | **오류 응답 형식이 두 가지다** | 게이트웨이 오류(401/404)는 `{"error":{"errorCode","message","details"}}`, 검색 오류(400)는 `{"errorMessage","errorCode"}`다. `x-ncp-apigw-response-origin` 헤더가 `APIGW`인지 `ENDPOINT`인지로 갈린다. **한쪽만 파싱하면 나머지 오류의 사유를 못 읽는다.** 본문 예시는 세 계열 모두 본문에 있다 — 401은 [4-2](#4-2-인증), 404는 [4-3](#4-3-엔드포인트와-요청)의 `.json` 항목, 400은 [4-3의 검색 오류(400) 응답 본문](#4-3-엔드포인트와-요청)(⚠️ **400만 재구성값**이고 실측 리터럴이 아니다 → [5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 11번) |
| **6** | **경로가 겹치거나 `.json`이 붙으면 404** | ① 개발자센터 시절 주소 습관으로 `.json`을 붙이는 경우. ② **`NAVER_API_BASE`에 채널 세그먼트까지 넣는 경우** — 기본값은 `.../search/v1`이고 코드가 `${BASE}/${endpoint}`로 조립하므로([`naver.ts:56,62`](../../apps/pipeline/src/collectors/naver.ts)), `.../search/v1/blog`를 넣으면 `/search/v1/blog/blog`가 된다. 둘 다 **게이트웨이 404**(`errorCode 300`)라 검색 오류 코드조차 안 나오고, 1번 때문에 **"성공, 0건"**으로만 보인다 |
| **7** | 🔴 **`sort` 기본값이 `sim`이다** | 안 주면 정확도순이라 **2019년 글이 첫 결과로 온다**(실측). 최신 모니터링이 목적이면 조용히 낡은 데이터를 쌓게 된다 |
| **8** | **카페는 작성일이 없다** | 기간 필터·날짜별 브리핑·트렌드에서 통째로 빠진다. 화면이 '작성일 미확인' 건수를 따로 보여주지 않으면 **345건이 사라진 것처럼 보인다** |
| **9** | `description`이 빈 문자열일 수 있다 | 카페 실측 최소 0자. `content`가 제목 한 줄만 남고, 그 상태로 LLM 분류에 들어간다 |
| **10** | `sourceId`가 URL이다 | 네이버가 URL 표기를 바꾸면(모바일/데스크톱, 파라미터 추가) **같은 글이 새 행으로 들어온다.** 중복 판정이 URL 문자열 일치에 걸려 있다 |
| **11** | 상한을 올려도 안 늘어난다 | 좁은 키워드는 이미 전부 가져오고 있다. 넓은 키워드는 100건으로 하루도 못 덮는다. → [4-5](#4-5-상한쿼터페이지네이션) |
| **12** | **검색 노이즈가 절반 가까이다** | 제목·본문 매칭이라 자사 서비스를 언급한 **채용 공고·홍보 글**이 대량으로 걸린다. 실측 관련 판정 비율은 블로그 67%, 카페 57%다. 분류 비용이 그만큼 더 나간다 |
| **13** | 확장할 수 있는 채널이 정해져 있다 | 쇼핑·책·전문자료는 **종료됐다**(2026-07-31 24:00, 약관 부칙 원문). 남은 것은 블로그·카페글·뉴스 등 일반 검색이다. 뉴스는 같은 키로 200이 뜬다(실측) |
| **14** | 개발자센터 키에는 만료일이 있다 | 2027-06-30 24:00까지만 제공된다(약관 부칙 제2조 ②④. ⚠️ 이 인용은 **대조 미완** → [2-2](#2-2-어느-약관이-적용되는가--먼저-이것부터-갈라야-한다)). 그날 이후 조용히 401로 바뀌고, 1번 때문에 **0건으로만 보인다** |
| **15** | 🔴 **요청 타임아웃을 안 걸면 수집 전체가 멈춘 것처럼 보인다** | 응답이 지연되면 **키워드마다 수 분씩 매달린다.** 키워드 9개 × 채널 2면 그 지연이 곱해져 배치가 끝나지 않는다. `fetch`에 **`AbortSignal.timeout(15_000)`을 반드시 건다**([`naver.ts:66-69`](../../apps/pipeline/src/collectors/naver.ts), 같은 취지의 주석이 [`naver.ts:65`](../../apps/pipeline/src/collectors/naver.ts)에 있다). **주의: 이 경로는 `res.ok` 분기가 아니라 `throw`로 빠진다.** 1번과는 다른 자리에서 조용해지므로 `fetch`를 `try/catch`로 감싸야 하고([`naver.ts:63-73`](../../apps/pipeline/src/collectors/naver.ts)), 안 감싸면 예외가 수집기 밖으로 튀어 그 서비스의 나머지 작업까지 죽는다 |
| **16** | 🔴 **`toISOString()`을 쓰면 날짜가 하루 밀린다** | `postdate`를 `new Date(...).toISOString()`으로 바꾸면 KST에서 `2026-08-29` → `2026-08-28T15:00:00.000Z`가 된다. 저장해야 하는 값은 `2026-08-29T00:00:00.000+09:00`이다. **오류도 안 나고 값도 그럴듯한데** 브리핑에서 하루가 밀리고, 다른 소스와의 **사전순 비교**가 깨진다 → [4-4](#4-4-응답--rawitem-매핑), 검증은 [5-2](#5-2-수집이-실제로-들어왔는지) |
| **17** | 변환표에 없는 HTML 엔티티가 원문 그대로 저장된다 | [`naver.ts:12-20`](../../apps/pipeline/src/collectors/naver.ts)의 `ENTITIES` 표는 `quot`·`amp`·`lt`·`gt`·`apos`·`nbsp`·`#39` **일곱 개뿐**이고, [`naver.ts:36`](../../apps/pipeline/src/collectors/naver.ts)의 `strip()`이 표에 없는 이름은 `?? m`으로 **그대로 되돌려 놓는다.** 그래서 `&#8230;` `&middot;` 같은 것이 오면 본문에 `&#8230;`이라는 글자가 남고 **그대로 LLM 입력이 된다.** 오류도 경고도 없다. 이걸 잡으려면 [5-2](#5-2-수집이-실제로-들어왔는지)의 검사가 **알려진 엔티티만이 아니라 `&...;` 패턴 전체**를 봐야 한다 |

> **1번과 2번이 이 문서에서 가장 중요한 항목이다.** 실제로 지금 DB의 네이버 데이터가
> 2026-08-18 이후 한 건도 늘지 않았고([1절](#30일-수집량-db-실측-2026-08-29)),
> 이 두 함정이 정확히 그런 증상을 만든다. **고치는 방법은 [5절](#5-붙인-뒤-확인할-것)에 있다.**

## 5. 붙인 뒤 확인할 것

### 5-1. 키가 살아 있는지 (10초, DB를 건드리지 않는다)

```bash
curl -s -o /dev/null -w "HTTP %{http_code}\n" \
  -H "X-NCP-APIGW-API-KEY-ID: $NAVER_CLIENT_ID" \
  -H "X-NCP-APIGW-API-KEY: $NAVER_CLIENT_SECRET" \
  --max-time 15 \
  "https://naverapihub.apigw.ntruss.com/search/v1/blog?query=test&display=1&sort=date"
```

응답 본문까지 봐야 원인이 갈린다(오류 형식이 두 가지다 → [4-6](#4-6-함정) 5번).
세 계열의 본문 모양은 [4-2](#4-2-인증)(401 실측)·[4-3](#4-3-엔드포인트와-요청)(404 실측, 400 재구성)에 있다.
헤더와 본문을 같이 찍으려면:

```bash
curl -s -D - \
  -H "X-NCP-APIGW-API-KEY-ID: $NAVER_CLIENT_ID" \
  -H "X-NCP-APIGW-API-KEY: $NAVER_CLIENT_SECRET" \
  --max-time 15 \
  "https://naverapihub.apigw.ntruss.com/search/v1/blog?query=test&display=1&sort=date"
```

**`HTTP 200`이면 정상.** 그 외는 아래 표로 원인을 가른다.

| HTTP | 본문 코드 | 원인 | 조치 |
|---|---|---|---|
| 200 | — | 정상 | — |
| 400 | `SE01` | `query`가 없거나 URL이 잘못됨 | 파라미터 확인 |
| 400 | `SE02` | `display`가 1~100 밖 | 값 확인 |
| 400 | `SE03` | `start`가 1~1000 밖 | 값 확인 |
| 400 | `SE04` | `sort` 오타 | `sim` 또는 `date` |
| 400 | `SE06` | 검색어 인코딩 문제 | UTF-8 퍼센트 인코딩 |
| **401** | `{"error":{"errorCode":"200"}}` | **헤더 이름이 틀렸거나 키 값이 틀렸다** | 본문의 "missing"을 믿지 말 것 ([4-2](#4-2-인증)) |
| 403 | — | 애플리케이션에 검색 API 사용 설정이 안 됨 | 콘솔에서 검색 API 이용 신청 확인. ⚠️ **여전히 확인 필요** — 이 해석은 개발자센터 문서 기준이고, HUB 공식 문서의 오류 표에는 **403 행 자체가 없다**(400 SE01~SE04·SE06 / 404 SE05 / 500 SE99가 전부다). 판별 → [5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 5번 |
| 404 | `{"error":{"errorCode":"300"}}` | 경로 오류 (`.json` 붙였거나 `NAVER_API_BASE`에 채널까지 넣어 경로가 겹침) | [4-3](#4-3-엔드포인트와-요청) |
| 404 | `SE05` | 존재하지 않는 검색 API | 엔드포인트 이름 확인 |
| 429 | ⚠️ 미확인 | 호출 한도 초과로 추정 | ⚠️ **확인 필요.** 잠정 정책은 **재시도 없이 중단 + `note` 기록** → [4-5의 호출 정책](#4-5-상한쿼터페이지네이션), 판별 → [5-4](#5-4-아직-확인되지-않은-것을-판별하는-절차) 2번 |
| 500 | `SE99` | 서버 오류 | **재시도 최대 2회, 1초 → 4초 백오프** ([4-5의 호출 정책](#4-5-상한쿼터페이지네이션)) |
| **(없음)** | — | **15초 안에 응답이 없음** | `AbortSignal.timeout`이 `throw`한다. `res.status`가 아예 없으므로 상태코드로 가르려 하면 안 잡힌다 → [4-6](#4-6-함정) 15번 |

### 5-2. 수집이 실제로 들어왔는지

한 번 돌린 뒤 아래를 본다. **"정상이면 이 숫자여야 한다"를 같이 적는다.**
(테이블은 `DATABASE_URL`의 `schema` 값 아래에 있다. 기본은 `feedback_radar`이므로
`SET search_path TO feedback_radar;`를 먼저 실행하거나 `feedback_radar.items`로 적는다.)

```sql
SELECT source,
       COUNT(*)                                   AS 건수,
       COUNT(*) FILTER (WHERE posted_at IS NULL)  AS 작성일없음,
       COUNT(*) FILTER (WHERE author IS NULL)     AS 작성자없음,
       -- 알려진 엔티티만 세면 '조용한 오염'(4-6 17번)을 정확히 놓친다.
       -- 남은 태그는 <...> 패턴 전체로, 엔티티는 &이름; / &#숫자; 패턴 전체로 잡는다.
       COUNT(*) FILTER (WHERE content LIKE '%<%>%'
                          OR content ~ '&#?[A-Za-z0-9]+;')   AS 태그잔존,
       -- 4-6 16번: toISOString()을 쓰면 여기서만 드러난다
       COUNT(*) FILTER (WHERE posted_at LIKE '%Z')            AS UTC저장사고,
       COUNT(*) FILTER (WHERE posted_at IS NOT NULL
                          AND posted_at NOT LIKE '%T00:00:00.000%') AS 시각이상,
       MIN(collected_at), MAX(collected_at)
  FROM items
 WHERE source LIKE 'naver%'
 GROUP BY source;
```

> **태그잔존을 `'%&quot;%'`처럼 아는 엔티티로만 검사하면 안 된다.** 그건 [`naver.ts:12-20`](../../apps/pipeline/src/collectors/naver.ts)의
> 변환표가 **이미 처리하는** 것들이라 정상이면 당연히 0이다. 정작 잡아야 할 것은 **변환표에 없는** 엔티티
> (`&#8230;` `&middot;` `&hellip;` 등)이고, 그건 표에 없다는 이유로 원문 그대로 남는다 → [4-6](#4-6-함정) 17번.

| 확인 항목 | 정상 | 비정상이면 |
|---|---|---|
| `naver-blog`의 **작성일없음** | **0** | 0이 아니면 `postdate` 파싱이 깨졌다 |
| `naver-cafe`의 **작성일없음** | **전체 건수와 같아야 한다** | 하나라도 채워져 있으면 매핑이 잘못됐다(카페는 원래 작성일이 없다) |
| **작성자없음** | **0** (실측 747/747 채워짐) | `bloggername`/`cafename` 매핑 확인 |
| **태그잔존** | **0** | `strip()`이 안 돌았거나(태그) **변환표에 없는 엔티티가 왔다**(→ [4-6](#4-6-함정) 17번). 0이 아니면 실제 값을 눈으로 봐야 한다: `SELECT content FROM items WHERE source LIKE 'naver%' AND content ~ '&#?[A-Za-z0-9]+;' LIMIT 20;` → 나온 엔티티를 `ENTITIES` 표에 추가한다 |
| **UTC저장사고** | **0** | 하나라도 있으면 `toISOString()`을 쓴 것이다. **저장된 날짜가 하루 밀려 있다** → [4-6](#4-6-함정) 16번. 재수집으로는 안 고쳐진다(`ON CONFLICT DO NOTHING`이라 기존 행이 그대로 남는다). 해당 행을 지우고 다시 받아야 한다 |
| **시각이상** | **0** | 블로그 `posted_at`은 전부 `T00:00:00.000`이어야 한다. 이 API는 날짜만 주기 때문이다. 0이 아니면 다른 소스와 섞였거나 매핑이 잘못됐다 |
| 블로그 `posted_at`의 **오프셋** | **`+09:00`** (KST 실행 기준. 실행 머신의 로컬 오프셋과 같아야 한다) | `Z`로 끝나면 **UTC 변환 사고**다(위 행). 값 하나를 직접 본다: `SELECT posted_at FROM items WHERE source='naver-blog' LIMIT 1;` → `2026-08-29T00:00:00.000+09:00` 모양이어야 한다 |
| 건수 — **첫 적재 회차에 한해서만** | 키워드 수 × **그 회차에 실제로 쓴 `display`** 이하. 실측 회차(키워드 9개, `display=50`)라면 **450건 이하** | 초과하면 중복 저장 의심. **두 번째 회차부터는 이 행을 쓰지 않는다** → 바로 아래 상자 |

> 🔴 **`건수` 행에는 시간 축이 붙어 있다. 첫 적재 회차에만 쓴다.**
> 위 SQL은 `items`의 네이버 행을 **누적으로** 센다. 그런데 저장이
> `ON CONFLICT (source, source_id) DO NOTHING`이라([`store.ts:236`](../../packages/core/src/store.ts))
> 회차가 쌓이면 총 건수는 **정상적으로** `키워드 수 × display`를 넘어간다. 이 단서를 빼면
> 며칠 뒤부터 건강한 적재가 매번 "중복 저장 의심"으로 잡힌다 — 기준이 오탐을 낸다.
>
> **회차 단위로 보려면 `items`가 아니라 `collect_progress`를 본다:**
>
> ```sql
> SELECT service, source, state, collected, inserted, note, started_at, ended_at
>   FROM collect_progress
>  WHERE source LIKE 'naver%'
>  ORDER BY seq;
> ```
>
> 행 하나가 **(서비스 × 채널) 작업 하나**다([`daily.ts:257,299-310`](../../apps/pipeline/src/daily.ts) —
> 서비스 루프 안에 채널 루프가 있다). 그러므로 정상 기준은 두 겹이다:
> **행별** `collected` ≤ (그 서비스의 키워드 수 × `display`), **`naver-blog` 행 전체 합** ≤ (키워드 합계 × `display`).
> `state`·`note`가 같은 행에 있으므로 [4-6](#4-6-함정) 1번의 "성공, 0건"도 여기서 같이 확인된다.
>
> ⚠️ **`display`는 회차마다 다를 수 있다.** 화면에서 조절하는 상한값이고 **코드 기본값 50 / 배포판 기본값 10**이다(→ [4-5](#4-5-상한쿼터페이지네이션)).
> 그 회차에 실제로 쓴 값은 실행 로그의 **`상한:` 줄**([`daily.ts:207-209`](../../apps/pipeline/src/daily.ts))에 찍힌다.
> 이 값을 모르고 450 같은 고정 숫자를 기준으로 삼으면 그 자체가 오탐이 된다.
>
> ⚠️ **단, 이 표는 회차마다 통째로 지워지고 다시 쓰인다** —
> [`store.ts:376`](../../packages/core/src/store.ts)이 `DELETE FROM ... collect_progress` 뒤에
> 이번 회차의 작업 목록을 다시 넣는다. **직전 회차 하나만 남는다.**
> 회차 사이 추이 비교는 지금 구조로는 불가능하고, [1절](#1-현황)이 실행 이력을 확정하지 못한 이유가 이것이다.

**건수 감각** (실측 기준): **감시 서비스 전체의 키워드 합계 9개**, `display=50`으로 첫 적재 시
블로그 402건 / 카페 345건이 들어왔다. 상한이 9 × 50 = **450건**이므로 두 숫자 모두 상한 안이다
(여러 키워드가 같은 글을 잡으면 `sourceId` 중복으로 빠지기 때문에 상한보다 적게 들어온다).
여기 쓴 "키워드 9개"는 [3-3](#3-3-우리가-실제로-얼마나-쓰나)·[`../api-costs.md`](../api-costs.md) 3절의
설정 실측값과 **같은 값, 같은 단위**다 — 한 회차가 전체 서비스를 한 번에 돌기 때문이다.
좁은 키워드라 **첫 실행에 과거 글까지 한꺼번에 들어오고, 그 뒤로는 하루에 몇 건 수준**이다.
따라서 **두 번째 실행부터 "신규 0~10건"은 정상**이다. 이 점 때문에 [4-6](#4-6-함정) 1번의
조용한 실패가 더 위험하다 — **정상적인 0건과 고장난 0건이 똑같아 보인다.**

### 5-3. 조용한 실패를 구별할 수 있게 만들기 (권고 조치)

지금 구조로는 위 5-2를 **사람이 주기적으로 들여다보는 수밖에 없다.** 코드로 고치려면:

1. **수집기가 실패 사유를 호출부에 돌려준다.** 지금은 오류를 삼키고 `[]`만 준다 —
   [`naver.ts:70-73`](../../apps/pipeline/src/collectors/naver.ts)(타임아웃·네트워크)와
   [`naver.ts:74-79`](../../apps/pipeline/src/collectors/naver.ts)(`!res.ok`)가 둘 다 `console.warn` 뒤 `return []`이다.
   `{ items, note }` 형태로 올려 [`daily.ts:458-461`](../../apps/pipeline/src/daily.ts)이
   `state: 'done', collected: 0`이 아니라 `state: 'failed'` 또는 `note`를 기록하게 한다.
   (`markCollectTask`는 이미 `note`를 받는다 — [`store.ts:379`](../../packages/core/src/store.ts).
   **필드를 새로 만들 필요가 없다. 값을 안 넣고 있을 뿐이다.**)
2. **`NAVER_CLIENT_SECRET` 누락을 `NAVER_CLIENT_ID`와 같은 급으로 검사한다.**
   [`naver.ts:102-105`](../../apps/pipeline/src/collectors/naver.ts)는 `NAVER_CLIENT_ID`만 보고 스킵 로그를 찍는데,
   실제 요청 함수의 [`naver.ts:59-61`](../../apps/pipeline/src/collectors/naver.ts) `if (!id || !secret) return []`은
   **로그를 한 줄도 안 남긴다.** 시크릿만 비면 키워드마다 조용히 0건이 된다
3. **"직전 성공 수집 시각"을 화면에 띄운다.** 이 채널은 정상 상태에서도 신규 0건이 잦아서,
   건수가 아니라 **마지막 성공 시각**이 유일하게 믿을 수 있는 신호다.
   데이터는 이미 있다 — `collect_progress`의 `ended_at`을
   [`store.ts:380`](../../packages/core/src/store.ts)의 `getCollectProgress()`가 `endedAt`으로 돌려주고,
   그것을 읽는 화면이 [`apps/web/app/page.tsx`](../../apps/web/app/page.tsx)다

> 이 셋은 자격증명도 외부 승인도 필요 없다. **고칠 파일은 셋이다** —
> [`apps/pipeline/src/collectors/naver.ts`](../../apps/pipeline/src/collectors/naver.ts)(1·2번),
> [`apps/pipeline/src/daily.ts`](../../apps/pipeline/src/daily.ts)(1번),
> [`apps/web/app/page.tsx`](../../apps/web/app/page.tsx)(3번).
> 1·2번만 하면 파이프라인 쪽 파일 두 개로 끝나고, 3번은 화면까지 건드린다.
> 적법성 문서 [7-2](../data-collection-compliance.md#7-2-robotstxt-준수를-코드에-넣는다)의
> "조용히 0건이 되면 안 된다"와 같은 취지다.
