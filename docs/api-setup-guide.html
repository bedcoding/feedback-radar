공식 API 연결 가이드

수집 채널을 정식 API로 붙이려면 사람이 어디 가서 무엇을 받아와야 하는지를 서비스별로 정리한 문서다. 코드 쪽 상세(엔드포인트·응답 매핑·함정)는 docs/sources/*.md에 있고, 이 문서는 그 앞단 — 키를 받기까지다.

기준일 2026-09-05. 회사·서비스·앱 이름은 쓰지 않는다. "판매자 계정마다", "개발자 계정마다"로 읽으면 된다.

먼저 알아둘 것 — 코드는 아직 정식 API로 바뀌지 않았다.
2026-08-29~30에 위반 경로를 전부 끈 것이지, 수집기를 고친 게 아니다. 아래 표의 "코드" 열이 ❌인 소스는 키를 받아도 그대로는 안 돈다 — 수집기를 새로 짜야 한다. X 하나만 코드가 이미 있어서 토큰을 넣으면 바로 켤 수 있다.

추천 순서

절차는 전부 지금 동시에 걸어라. 리드타임이 개발 손 밖에 있어서(다른 부서 승인, 결제, 외부 심사) 늦게 걸수록 순서와 무관하게 밀린다.

순서소스왜 이 자리외부 의존
1X코드가 이미 있다. 토큰만 있으면 오늘 켤 수 있다결제수단 등록
2앱스토어 + 구글플레이심각 이슈 밀도가 가장 높다(부정 73%·58%). 외부 심사가 없다각 계정 관리자의 키 발급·권한 승인
3Threads리드타임 최장. 법인 인증 + 앱 심사Meta — 기간 보장 없음

네이버는 이미 돌고 있고, 나머지(디시·더쿠·다음 카페)는 API 연결 대상이 아니다.

X (트위터) — 토큰만 넣으면 켜진다

코드 있음 apps/pipeline/src/collectors/x.ts가 공식 API를 이미 호출한다. 할 일은 토큰 발급 → .env → 설정에서 경로를 api로 셋이다.

누가 필요한가

개발계정 생성, 앱 생성, 토큰 발급 재무/구매결제수단 등록. 2026-02부터 무료 등급이 없어 신규는 종량제뿐이다. 이게 실질 리드타임이다 법무용도를 상업적(commercial)으로 신고하는 것 확인. VOC 모니터링은 "by or for a business"에 해당한다

절차

  1. X 계정에 전화번호 인증을 해 둔다 (개발자 약관 조건)
  2. console.x.com 접속 → Accept the Developer Agreement
  3. New App → 앱 이름·용도 입력. 용도는 commercial로
  4. 결제수단 등록 + 청구 주기당 지출 한도(spend limit) 설정. 코드의 월 예산($50 기본)은 앞단 브레이크일 뿐이라 콘솔 쪽도 반드시 건다
  5. 앱의 Keys and tokens에서 Bearer Token 생성. 같은 화면의 API Key / API Key Secret도 함께 보관 — 나중에 토큰을 다시 만들 때 필요하다
  6. 🔴 자격증명은 한 번만 보인다. 닫기 전에 비밀 관리 도구에 넣는다

.env

X_BEARER_TOKEN=<Bearer Token>

설정 화면에서

  1. 대시보드 → 설정 탭 → 수집량 카드의 X 경로를 web에서 api로
  2. X 회당 상한(xPosts)과 월 예산 확인. 기본 키워드당 20건, 예산 $50
  3. 소스 토글에서 X 켜기

비용 감각

읽기 1건 $0.005. 같은 UTC 하루 안에 같은 포스트를 다시 읽으면 재과금이 없다(공식 명시). 그래서 현실값은 월 $1~3, 상한 시나리오(매 회차 전부 새 글)는 24시간 주기 $27, 6시간 $108. 비용을 줄이는 손잡이는 주기가 아니라 키워드 수다.

함정. 공식 API는 키워드를 따옴표로 감싼 정확 구문 검색이라 공백 든 키워드가 web 경로보다 적게 잡힌다. 그리고 긴 글은 본문이 잘려 오므로 note_tweet 필드를 요청에 추가해야 전문이 온다 — 지금 코드는 안 하고 있다. 상세는 docs/sources/x.md 4-6.

시작 가이드 가격 개발자 콘솔

앱스토어 — 판매자 계정마다 키 1벌

코드 없음 지금 수집기는 iTunes RSS를 친다. 키를 받은 뒤 App Store Connect API 수집기를 새로 짜야 한다 (설계는 docs/sources/appstore.md 4절에 있다).

왜 키가 여러 벌인가. App Store Connect API 키는 판매자 계정 단위다. 자사 앱이 법인별로 다른 판매자 계정에 나뉘어 있으면 계정마다 1벌 필요하다. 어느 앱이 어느 계정인지는 App Store 앱 페이지의 "판매자" 표기로 확인한다.

누가 필요한가

각 계정 Admin팀 키 생성은 Admin만 가능하다. 개발자가 그 계정에 Admin이 아니면 요청해야 한다 — 여기서 일정이 개발 손 밖으로 나간다 개발받은 값을 .env에 넣고 수집기 작성

절차 (판매자 계정마다 반복)

  1. App Store Connect → 사용자 및 액세스(Users and Access) → 통합(Integrations) 탭 → 왼쪽 App Store Connect API
  2. 팀 키(Team Keys) 탭 → + (Generate API Key)
  3. 이름은 참조용. Access(역할)는 Customer Support를 먼저 시도 — 설명이 "고객 리뷰 분석·응답"이라 최소 권한이다. 첫 호출이 403이면 Admin으로 재발급 (Apple이 엔드포인트별 필요 역할표를 안 준다)
  4. .p8 파일 다운로드 🔴 1회 한정. Apple은 사본을 보관하지 않는다. 링크는 한 번 받으면 사라진다. 받는 즉시 비밀 관리 도구에 넣는다
  5. 같은 화면에서 Key ID(10자) 복사
  6. 페이지 상단의 Issuer ID(UUID) 복사
  7. 세 값(.p8 · Key ID · Issuer ID)을 개발에 안전한 경로로 전달. 🔴 저장소에 커밋하지 않는다 — Apple 약관이 명시적으로 금지한다
팀 키를 쓴다, 개인 키가 아니라. 개인 키는 그 사람의 권한에 묶여 퇴사·역할 변경 시 조용히 죽는다. 상주 파이프라인에는 팀 키다.

.env (계정마다 한 묶음)

# 계정 A
ASC_KEY_A_ISSUER_ID=<Issuer ID>
ASC_KEY_A_KEY_ID=<Key ID>
ASC_KEY_A_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----
...p8 파일 내용 전문...
-----END PRIVATE KEY-----"
# 계정 B도 같은 형식으로. 서비스 설정에서 앱마다 어느 키를 쓸지 지정한다

변수 이름은 docs/sources/appstore.md 4-2의 설계를 따른 것이다. 수집기를 짤 때 그 문서와 맞춘다.

받은 뒤 바로 확인할 것

# JWT를 만들어 이 한 줄이 200을 주면 키·역할이 맞은 것이다 (JWT 생성 코드는 appstore.md 4-2)
curl -H "Authorization: Bearer $JWT" \
  "https://api.appstoreconnect.apple.com/v1/apps?limit=1"
# 403 → 역할 부족 (Admin으로 재발급) / 401 → JWT 서명 문제 (dsaEncoding: ieee-p1363 확인)
알아둘 것 두 가지. ① 이 API로 바꾸면 기존 앱스토어 데이터 전량이 재적재된다 — RSS와 리뷰 ID 체계가 달라 중복 판정이 이어지지 않는다. 방침(재적재 감수 / 마이그레이션 / 새 계열 시작)을 먼저 정한다. ② 자사 앱만 읽을 수 있다. 지금 대상이 전부 자사 앱이라 손실은 없지만, 경쟁사 앱은 영구히 못 본다.

키 생성 문서 customerReviews 엔드포인트 호출 한도

구글플레이 — 서비스 계정 1벌 + 개발자 계정마다 초대

코드 없음 지금 수집기는 google-play-scraper를 쓴다. 권한이 나온 뒤 Play Developer API 수집기를 새로 짜야 한다 (설계는 docs/sources/googleplay.md 4절).

앱스토어와 다르다 — 키는 1벌이다. 서비스 계정 하나를 만들고 그 이메일을 개발자 계정마다 사용자로 초대하면 된다. 필요한 건 키 N벌이 아니라 권한 부여 N건이다.

누가 필요한가

개발GCP 프로젝트·서비스 계정 생성, JSON 키 다운로드 각 개발자 계정 관리자Play Console에서 서비스 계정 이메일을 초대하고 '리뷰 답글' 권한을 준다. 계정 수만큼의 승인이 필요하다

절차 ① — 개발이 한 번만

  1. Google Cloud Console → 프로젝트 생성 (또는 기존 프로젝트)
  2. API 및 서비스 → 라이브러리 → Google Play Android Developer API 검색 → 사용(Enable)
  3. IAM 및 관리자 → 서비스 계정 → 서비스 계정 만들기. 역할은 안 줘도 된다 (권한은 Play Console 쪽에서 준다)
  4. 만든 서비스 계정 → 키 탭 → 키 추가 → 새 키 만들기 → JSON → 다운로드. 이 JSON 파일이 자격증명 전부다
  5. JSON 안의 client_email(…@….iam.gserviceaccount.com)을 복사 — 아래 초대에 쓴다

절차 ② — 개발자 계정마다 (관리자가)

  1. Play Console → 왼쪽 사용자 및 권한(Users and permissions)
  2. 새 사용자 초대(Invite new users) → 이메일 칸에 위 client_email
  3. 권한에서 🔴 "리뷰 답글(Reply to reviews)"을 준다. "앱 정보 보기(View app information)"만으로는 리뷰 API가 안 열린다 — 읽기만 할 건데 '답글' 권한을 요청하는 게 어색해 보여도 이게 맞다. 요청 메일에 권한 이름을 그대로 적어라
  4. 범위는 계정 전체 또는 대상 앱만. 사용자 초대(Invite user)
GCP 프로젝트를 Play Console에 "연결(link)"하는 단계는 없다. 공식 문서: "You no longer need to link your developer account to a Google Cloud Project." 예전 자료에 나오는 그 단계는 건너뛴다.

.env

# 서비스 계정 JSON 파일 내용을 한 줄로 통째로
GOOGLE_PLAY_SA_JSON={"type":"service_account","project_id":"...","client_email":"...","private_key":"-----BEGIN PRIVATE KEY-----\n...\n-----END PRIVATE KEY-----\n",...}

🔴 private_key의 줄바꿈이 리터럴 \n 두 글자로 들어와야 한다. 파일을 그대로 붙이면 실제 줄바꿈이 돼서 .env 파서가 깨진다.

받은 뒤 바로 확인할 것

# 서비스 계정으로 토큰 발급(RS256 JWT, googleplay.md 4-2) 후:
curl -H "Authorization: Bearer $TOKEN" \
  "https://androidpublisher.googleapis.com/androidpublisher/v3/applications/<패키지명>/reviews?maxResults=1"
# 403 → 그 개발자 계정에서 초대·권한이 아직 안 됐다 (앱 단위 부분 실패 가능)
# 200에 빈 배열 → 정상일 수 있다: 이 API는 최근 7일 리뷰만 준다
알아둘 것. ① 🔴 최근 7일 안에 작성·수정된 리뷰만 온다 (공식 원문). 스케줄러가 일주일 넘게 멈추면 그 구간은 영구 유실. 과거분은 Play Console → 리뷰 → CSV 내려받기로 1회 채운다. ② 페이지당 최대 100건 — nextPageToken 루프 없이 짜면 100건에서 조용히 끊긴다. ③ 쿼터 앱당 GET 200회/시간.

시작 가이드 리뷰 API (7일 창 원문) reviews.list

Threads — 개발자 혼자 못 끝낸다

코드 없음 지금 수집기는 Playwright로 threads.com/search를 연다. 공식 API로 바꾸려면 외부 승인 3단계가 앞에 있고, Meta는 기간을 보장하지 않는다. 승인 나면 수집기를 새로 짠다 (설계는 docs/sources/threads.md 4절).

핵심 제약. 공식 API keyword_search는 threads_keyword_search 권한 승인 전에는 인증한 계정 본인의 글만 검색된다. 타인의 공개 글을 검색하려면 고급 액세스가 필요하고, 그건 법인 비즈니스 인증 + 앱 심사를 둘 다 통과해야 한다.

누가 필요한가

개발Meta 앱 생성, OAuth 콜백 구현, 토큰 교환·갱신 코드 법무 / 경영지원🔴 비즈니스 인증 — 사업자등록증 등 법인 실체 증빙과 대표 정보를 Meta에 제출. 개발자가 낼 수 없다 비즈니스 포트폴리오 관리자인증된 비즈니스에 앱을 연결 운영 담당토큰을 묶을 운영용 Threads 계정 결정. 개인 계정이면 퇴사·변경 시 토큰이 통째로 죽는다

절차

  1. developers.facebook.com → 개발자 등록 → 앱 만들기 → 유스케이스에서 Threads 선택. 앱 ID/시크릿이 두 쌍 나오는데 Threads 쪽을 쓴다
  2. 🔴 비즈니스 인증(Business Verification) — 앱 대시보드 → 앱 설정 → 기본 설정 → 비즈니스 인증. 법인 서류 제출. 지금 바로 걸어라, 가장 오래 걸린다
  3. 비즈니스 포트폴리오에 앱 연결
  4. OAuth 콜백 주소(HTTPS)를 앱 설정에 등록. 🔴 이 저장소에는 지금 그런 주소가 없다 — 배포 도메인이나 로컬 터널이 필요하다
  5. 운영 계정으로 Authorization Window 한 번 통과 → 1시간짜리 단기 토큰 → /access_token으로 60일 장기 토큰으로 교환
  6. 🔴 승인 전에 인증 계정으로 keyword_search를 최소 1회 호출해 둔다. 앱 심사 조건이 "요청 권한마다 성공한 API 호출 1회 이상"이라, 승인 기다렸다가 처음 호출하면 심사가 안 통과된다 (순환 조건)
  7. 앱 심사(App Review)에서 threads_keyword_search 요청. 용도 설명 + 화면 녹화 제출. 앱은 게시(published) 상태여야 한다
  8. 승인 후 → 수집기 작성 → 켠다

.env / 설정

THREADS_APP_ID=<Threads 앱 ID>
THREADS_APP_SECRET=<Threads 앱 시크릿>
# 장기 토큰은 60일마다 갱신해야 한다. 환경변수는 프로세스가 다시 쓸 수 없으므로
# settings 표에 토큰 + 발급시각을 저장하는 설계가 필요하다 (threads.md 4-2). 이 저장소에 선례가 없다.

네이버 — 이미 연결됨

코드 있음 · 켜짐 유일하게 돌고 있는 경로다. 새로 할 건 없고, 어디서 받은 키인지와 약관 미결 항목만 알아두면 된다.

2026년부터 발급처가 바뀌었다. 개발자센터(developers.naver.com)에서는 검색 API 신규 발급이 안 된다. NAVER Cloud Platform의 NAVER API HUB에서 받는다. 변수 이름은 옛날 그대로 NAVER_CLIENT_*인데 값은 NCP 키다 — 이름 보고 개발자센터 키를 넣으면 401.

키를 새로 받아야 할 때

  1. NAVER Cloud Platform 콘솔 (계정·결제 권한자)
  2. NAVER API HUB → 검색 API 이용 신청
  3. 발급된 API Key ID / API Key 두 값

.env

NAVER_CLIENT_ID=<NCP API Key ID>
NAVER_CLIENT_SECRET=<NCP API Key>
# NAVER_API_BASE는 건드리지 않는다. /blog 같은 채널 세그먼트를 붙이면 경로가 겹쳐 404가 나는데
# 화면에는 "성공, 0건"으로 보인다.

비용·한도

현재 0원. 검색 카테고리 통합 일 25,000건(월 775,000건은 그 누적일 뿐, 몰아 쓸 수 없다). 키당 50 RPS. "한시적 무료 제공 정책은 추후 변경될 수 있습니다"가 요금표에 적혀 있고 유료 전환 후 단가는 미공표 — 요금 공지를 받을 수 있게 해 두는 게 좋다.

미결 — 법무 검토 1순위. 개발자센터 약관 7.3 ③이 "저장(캐시 행위 포함)"을 제한한다. 절대 금지는 아니고 "API의 제공 취지에 맞는가"가 기준인데, 이 도구는 결과를 영구 적재하고 LLM에 전달한다. 지금 돌고 있는 유일한 경로라 우선순위가 가장 높다. 상세는 docs/data-collection-compliance.md 4-1.

NAVER API HUB 요금 개발자센터 약관 (7.3 ③)

API로 연결하지 않는 것

소스왜되살릴 유일한 길
디시인사이드공식 API 없음. 이용약관 제16조 ①이 사전 서면 동의 없는 크롤링을 금지그 조항이 스스로 명시한 "사전 서면 동의"를 받는 것
더쿠공식 API 없음. robots.txt도 약관도 없는 회색지대 — 방침에 따라 접음운영진 서면 허가. 요청서 항목은 docs/sources/theqoo.md 4-1
다음 카페카카오 검색 API가 있지만 운영정책 제5조 20호가 "사용자 환경 개선 외 목적의 캐시 / 최신성 유지 없는 캐시"를 금지. 이 도구의 영구 적재가 정면으로 걸린다. API로 옮기면 리스크가 없어지는 게 아니라 새로 생긴다법무 판단 선행. 통과 못 하면 현재 모바일 웹 경로(robots.txt가 명시적 Allow)가 오히려 근거가 낫다

디시·더쿠는 같은 문서 한 벌로 두 곳에 요청할 수 있다 — 목적, 수집 범위, 요청 빈도, 저장 범위, 용도, 중단 요청 창구.

.env 한눈에

# ── 지금 쓰는 것 ──
NAVER_CLIENT_ID=            # NCP API Key ID (개발자센터 키 아님)
NAVER_CLIENT_SECRET=        # NCP API Key
X_BEARER_TOKEN=             # 넣고 설정에서 X 경로를 api로 → 켜면 바로 동작

# ── 수집기를 새로 짠 뒤에 쓰는 것 (지금 넣어도 코드가 읽지 않는다) ──
ASC_KEY_A_ISSUER_ID=        # 앱스토어 판매자 계정 A
ASC_KEY_A_KEY_ID=
ASC_KEY_A_PRIVATE_KEY=      # .p8 전문
ASC_KEY_B_ISSUER_ID=        # 계정 B …
GOOGLE_PLAY_SA_JSON=        # 서비스 계정 JSON 한 줄 (private_key 줄바꿈은 \n 리터럴)
THREADS_APP_ID=
THREADS_APP_SECRET=         # 장기 토큰은 settings 표에 저장 (60일 회전)

🔴 .env와 private/는 gitignore다. 키·토큰·.p8·JSON은 어떤 형태로도 커밋하지 않는다. 소스별 문서에 자리표시자로만 적혀 있는 이유다.
